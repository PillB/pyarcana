### S46-F06 🚩 — allowed lateness is incorrectly modeled as watermark-minus-event grace and propagates across theory/figure/I Do/We Do/self-check/You Do
- **Category:** technical/event-time
- **Location:** T1-A theory + S46-event-time figure + I Do + We Do + selfCheck + You Do
- **Evidence:** Canonical example uses window_end=120, watermark=110 and labels event_time=105 ALLOWED_LATE even though the watermark has not yet passed that window's end. Current Flink docs define allowed lateness from window end until window end + allowed lateness.
- **Impact:** The core concept is wrong across explanation, diagram, worked example, exercises, fallback assessment and final project. Learners can be graded correct for a model incompatible with the reference systems the section cites.
- **Attack:** Apply the canonical numbers to event-time window lifecycle semantics in Flink/Beam-style systems.
- **Defense:** The paragraph explicitly calls the model a simplification for a stdlib lab.
- **Proposed fix:** Model a concrete window `[window_start, window_end)`. `ON_TIME` while watermark <= window_end; after the watermark crosses window_end, events assigned to that window are late-but-accepted until watermark > window_end + allowed_lateness; later arrivals go to side output/drop according to policy.
- **Verdict:** CONFIRMED P0 because the simplification changes the construct being named, not merely the implementation detail.
