## P1 (6)

### S01-F04 — The learner receives incompatible runtime contracts for the same gate.
- **Category:** TECHNICAL_CONTRADICTION
- **Location:** learning outcomes + interpreter paragraphs + stack verification + Ruff config
- **Evidence:** Outcome requires Python 3.12+, multiple paragraphs say 3.10+ is acceptable, while Ruff target-version is py312.
- **Impact:** A learner on 3.10 cannot determine whether to continue, upgrade, or alter Ruff; subsequent reproducibility evidence no longer has one target runtime.
- **Proposed fix:** Choose one supported floor and state it everywhere. Current roadmap and config point to 3.12+.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F06 — The example uses future syntax to teach a concept that can be demonstrated with one print statement, and the callout falsely makes def + __name__ guard sound necessary for scripts.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** theory[2].paragraphs[3-4] + hello_sys.py + REPL/script callout
- **Evidence:** The first script introduces import, def, indentation, variables, method calls, indexing, f-strings and if __name__ before those concepts are taught; the callout says a .py uses def + if __name__.
- **Impact:** The learner memorizes a template without being able to explain or predict its parts and can incorrectly believe every script requires main() and an __name__ guard.
- **Proposed fix:** Replace the first script with a single print statement; defer main/import/f-string/__name__ until their real teaching sections.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F08 — A transcript and an executable command block are represented as the same thing.
- **Category:** EXAMPLE_CONTRADICTS_EXECUTION_INSTRUCTIONS
- **Location:** theory block 'El intérprete en la terminal' code
- **Evidence:** The prose calls the block 'copy-paste real'; it starts an interactive python3 REPL but the following REPL commands are shell-style commented transcript lines, so pasting the full block cannot execute the demonstrated interaction and exit as claimed.
- **Impact:** The learner pastes the block, enters the REPL, comments out the supposed expressions/quit command, and gets stuck or sends later shell commands to Python.
- **Proposed fix:** Label it as a transcript or split shell commands and REPL keystrokes into separate clearly typed blocks.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F10 — The learner must understand several later Python constructs to understand the example used for a much simpler process contract.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** theory block 'Terminal, rutas y códigos de salida' argv paragraph + check_arg.py
- **Evidence:** S01 teaches sys.argv as a list, indexing, len, slicing, stderr, a function, conditional and type annotation to demonstrate exit codes.
- **Impact:** The learner can only copy check_arg.py and cannot explain why len==2, what [1:] means, or why the branch exits 1.
- **Proposed fix:** Remove argv/slicing from S01 theory and demonstrate exit 0/1 with prepared one-liners; teach CLI arguments in the later CLI section.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F11 — The error-suppression example undermines the core mental model rather than extending it safely.
- **Category:** TECHNICAL_CONTRADICTION
- **Location:** 'Leer una línea de terminal' final paragraph
- **Evidence:** The lesson emphasizes exit status as evidence, then introduces 2>/dev/null \|\| true as a starter pattern without saying that \|\| true can turn a failure into overall success and erase the signal just taught.
- **Impact:** The learner can adopt 'append \|\| true when a command is noisy/fails' and cause a script or CI step to report success after a real failure.
- **Proposed fix:** Remove this pattern from core S01. If retained in optional troubleshooting, explicitly explain that it masks failure and is valid only when failure is intentionally non-fatal.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F17 — A privacy-sensitive first-day workflow asks the learner to persist a real email globally without informed choice.
- **Category:** PRIVACY_RISK
- **Location:** Git identity paragraph + git config code
- **Evidence:** The lesson instructs git config --global user.email 'tu@correo.com' immediately before publishing to GitHub, but gives no warning that commit email metadata can expose a personal address or that GitHub provides a noreply address.
- **Impact:** A learner follows the command literally, pushes a public repository and exposes a personal email in commit metadata.
- **Proposed fix:** Before the command, explain commit-email visibility and offer the GitHub noreply address; advise --local when personal/work identities differ.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

## P2 (13)

### S01-F01 — The time promise cannot be satisfied at the upper end and the phrase 'resto' has no coherent remainder in a 10 h section.
- **Category:** PROMISE_CONTRADICTION
- **Location:** tagline + optional contract timing
- **Evidence:** Tagline allocates 3–4 h to core plus 6–8 h to GitHub/Ruff plus remaining time for CP-N1-A, while theory states about 10 h total.
- **Impact:** The learner cannot tell what is core, optional, or expected within the advertised section duration and may interpret unfinished material as personal failure.

- **Sources (1):** audit/lessons-only/lesson_audit_log.json

- **Evidence:** The Mars Climate Orbiter paragraph says nobody made a calculation error and reduces the mishap to two teams assuming different units.
- **Impact:** The learner forms an oversimplified causal model in the very example used to justify explicit contracts and verification.
- **Proposed fix:** Keep the incident but state the metric/English-unit interface failure and that project controls did not detect it.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F03 — Internal curriculum identifiers are used as though they carry meaning for a first-day learner.
- **Category:** WIDOW_TERM
- **Location:** tagline + theory[0].paragraphs[4] + optional contract
- **Evidence:** CP-N1-A and CASO-LIM-001 appear before a learner-facing explanation of what those labels represent.

### S01-F05 — Remote execution is not a defining property of a script.
- **Category:** EXAMPLE_CONTRADICTS_PROSE
- **Location:** figure S01-repl-vs-script
- **Evidence:** Caption defines a script as a file that runs whole 'en una máquina que no es la tuya', while the prose tells the learner to run python hello.py locally.
- **Impact:** The learner may classify local .py execution as something other than a script or associate scripts primarily with servers/pipelines.
- **Proposed fix:** Define the contrast as interactive one-expression-at-a-time execution versus saved-file execution; remove the remote-machine property.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F07 — The learner receives an inaccurate forward map of when this syntax becomes learnable.

### S01-F09 — Terminal and shell change from distinct conceptual levels into synonyms.
- **Category:** DEFINITION_DRIFT
- **Location:** opening definitions + 'Terminal, rutas y códigos de salida'
- **Evidence:** Opening defines terminal as the text window; later prose calls bash, zsh and PowerShell 'la terminal'.
- **Impact:** A Windows learner cannot understand why the same terminal application can host PowerShell or another shell with different syntax.
- **Proposed fix:** Add one sentence: terminal is the application/window; shell is the command interpreter inside it, e.g. PowerShell, bash or zsh.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F12 — Too many independent shell operators and platform branches must be held in working memory before they are needed for the section's core reproducibility model.
- **Category:** COGNITIVE_LOAD_HIGH
- **Location:** 'Leer una línea de terminal: los conectores del día 1'
- **Evidence:** Before the learner reaches venv, one block adds >, >>, \|, head, grep, &&, \|\|, mkdir, rm -rf, which/where and stderr redirection.
- **Impact:** When a later venv/pip command fails, the learner has to distinguish environment failure from a large new shell syntax vocabulary and may debug the wrong layer.
- **Proposed fix:** Keep only commands required immediately; move pipes/filters/error redirection/destructive cleanup to optional reference or introduce each immediately before first essential use.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F13 — The isolation model is stronger than the portability model actually guaranteed by venv.
- **Category:** MISCONCEPTION_RISK
- **Location:** jobRelevance + opening environment definition + venv paragraph
- **Evidence:** The environment is repeatedly described as a self-contained folder with 'its own Python'; Python documentation says venvs are disposable and not considered movable/copyable.
- **Impact:** The learner can conclude that copying .venv to another machine is a valid reproducibility strategy because the folder supposedly contains a self-contained Python.
- **Proposed fix:** Define it as an isolated directory with a Python associated with that environment and its site-packages, then explicitly say it is recreated rather than copied.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F14 — A platform-specific failure mode interrupts the first exposure before the learner has stabilized the base concept.
- **Category:** PROGRESSIVE_DISCLOSURE_DEFECT
- **Location:** venv paragraph 1
- **Evidence:** Debian/Ubuntu ensurepip/package-manager recovery is embedded in the first core definition of venv.
- **Impact:** A learner on macOS/Windows must process apt, ensurepip and distro packaging despite none being relevant; a Linux learner sees recovery syntax before understanding what successful creation should mean.
- **Proposed fix:** Move distro-specific repair into a troubleshooting callout after the successful model and verification.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F15 — The learner is told what suffix the output should have without understanding why that value proves the active environment.
- **Category:** WIDOW_TERM
- **Location:** venv code + .venv/.env callout
- **Evidence:** sys.prefix is used as proof that the venv is active but the lesson does not define what sys.prefix represents.
- **Impact:** The learner pattern-matches '.venv' rather than understanding the diagnostic and cannot adapt it when paths differ.
- **Proposed fix:** Add a microdefinition: sys.prefix is the directory Python reports as the active environment prefix.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F16 — The example advertises the reconstruction action central to reproducibility but only demonstrates install/freeze/import in the same environment.
- **Category:** EXAMPLE_SCOPE_MISMATCH
- **Location:** pip code title and body
- **Evidence:** The code block is titled 'install, freeze, install -r' but never executes python -m pip install -r requirements.txt.
- **Impact:** The learner may think they have seen/tested the clean reconstruction step when the code never performs it.
- **Proposed fix:** Either rename the block to its actual scope or add an explicit clean-environment install -r demonstration without pretending same-venv reinstall proves portability.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F18 — The recovery contract is incomplete for the exact novice state most likely to contain newly created untracked files.
- **Category:** TECHNICAL_OVERGENERALIZATION
- **Location:** branches/recovery paragraph
- **Evidence:** The prose says git stash stores temporary changes and leaves the tree clean without stating that untracked files are not included by default; Git documents -u/--include-untracked for that behavior.
- **Impact:** The learner stashes before switching context, assumes a clean tree, and is surprised that new untracked files remain; they may then misdiagnose Git or accidentally leave sensitive files exposed.
- **Proposed fix:** Say stash handles tracked modifications by default; use git stash -u only when deliberately including untracked files, and verify with git status.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json

### S01-F19 — A key security artifact is demonstrated with syntax a Windows learner cannot execute, while another unexplained delivery concept is used to justify Ruff.
- **Category:** WIDOW_TERM_AND_PLATFORM_BLOCKER
- **Location:** Ruff callout + quality-files paragraph/code
- **Evidence:** CI is used without a microdefinition; the core .gitignore/.env.example creation block uses Bash heredoc syntax even though S01 promises Windows PowerShell support.
- **Impact:** The Windows learner receives a syntax error when creating .gitignore and cannot know whether Git, the file content or the shell is wrong; the CI comparison adds an unexplained dependency.
- **Proposed fix:** Define CI in one clause and create these tiny files through VS Code with content blocks, then verify with git check-ignore; avoid heredoc as the canonical cross-platform path.
- **Sources (1):** audit/lessons-only/lesson_audit_log.json
