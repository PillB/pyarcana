## P1 (11)

### S05-F01 — A function contract includes behavioral guarantees, not only the visible signature or input/output shape. Internal code can change without changing the signature and still violate the postcondition.
- **Category:** FALSE_CORE_MENTAL_MODEL_CONTRACT
- **Location:** S05-T1-A figure S05-contract caption
- **Evidence:** The caption says implementation is inside the box and 'Cambiar el cuerpo sin tocar los bordes es libre'.
- **Impact:** Due to this problem, a learner can believe that any body-only change is a safe refactor as long as the parameters and return shape stay unchanged.
- **Proposed fix:** Change the caption to say the implementation may change only while preserving the contract: preconditions, outputs, errors and observable effects.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F02 — The example intended to teach definition/call/return requires the learner to decode several unrelated transformations before they can trace the function boundary.
- **Category:** EXAMPLE_OVERLOADED_FUTURE_KNOWLEDGE_LEAK
- **Location:** S05-T1-A paragraphs 2-5 + def_return.py
- **Evidence:** The first worked function uses raw.strip().split(), join(), title(), annotations and a second no-return function while string methods are formally S07 and function mechanics are new here.
- **Impact:** Due to this problem, a learner can reproduce normalize_nombre while still being unable to explain when a def body runs, how raw receives an argument or how return hands a value back.
- **Proposed fix:** Start T1-A with a one-operation function whose body uses already-earned syntax, trace definition -> call -> parameter binding -> return, then introduce normalize_nombre after the function model exists.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F03 — The roadmap requires safe defaults before it teaches the mutable structures that make the default bug understandable; the lesson uses those structures without a bounded micro-model.
- **Category:** ROADMAP_PREREQUISITE_CONFLICT_FUTURE_KNOWLEDGE_LEAK
- **Location:** S05-T1-B mutable-default explanation and params_defaults.py
- **Evidence:** The key safe-default outcome is taught using [] lists, append(), shared-object mutation and list-return behavior although S06 is the first collection lesson and the prior ledger does not credit list mutation mastery.
- **Impact:** Due to this problem, a learner can memorize 'use None' without understanding that one mutable default object is created once and then changed across calls.
- **Proposed fix:** Add an explicit micro-model: a list is a changeable container; the default object is created once at def time; append changes that same object. Keep the detailed collection mechanics for S06.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F06 — The lesson does not distinguish an assumed caller obligation from a runtime validation performed by the callee or by an external boundary.
- **Category:** CONTRACT_ENFORCEMENT_CONTRADICTION
- **Location:** S05-T2-A figure caption + paragraphs 1-4 + docstring_email.py
- **Evidence:** Prose defines a precondition as what must be true before calling; the figure says the precondition 'se comprueba antes de tocar nada'; the example states 'Pre: raw es str' but performs no explicit type check and would raise AttributeError for None/int.
- **Impact:** Due to this problem, a learner cannot tell whether every documented precondition must be checked inside the function, is automatically enforced by Python, or is merely required of callers.
- **Proposed fix:** Add one sentence: a precondition states what callers must provide; it may be assumed inside trusted core code or explicitly validated at an untrusted boundary. Make the figure say 'declarar/validar según el boundary', not that every precondition is automatically checked.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F08 — The worked example violates the section's own gradual-hints rule and makes type syntax plus tuple semantics prerequisites for understanding domain errors.
- **Category:** EXAMPLE_CONTRADICTS_PROGRESSIVE_DISCLOSURE_FUTURE_COLLECTION
- **Location:** S05-T2-B paragraphs 2-5 + hints_dominio.py
- **Evidence:** The prose says not to overload S05 with advanced generics, then immediately imports Optional and Tuple and uses Tuple[bool, Optional[int], Optional[str]], a three-field tuple result, before S06 teaches tuples and structured collections.
- **Impact:** Due to this problem, a learner can interpret type hints as a nested mini-language they must master immediately and cannot distinguish the function's domain-error idea from its result-container syntax.
- **Proposed fix:** Keep T2-B examples to simple public annotations such as raw: str -> str; postpone Optional/Tuple result protocols to S06 or introduce one bounded str \| None form only when it is genuinely needed.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F09 — S05 legitimately needs to state domain-error behavior, but it asks the learner to trace exception control flow without first teaching what raise interrupts, what except catches, or where execution res
- **Category:** ROADMAP_PREREQUISITE_CONFLICT_EXCEPTION_FLOW
- **Location:** S05-T2-A/T2-B code and callouts
- **Evidence:** normalize_email raises ValueError and theory demonstrates try/except; parse_edad also uses try/except, while the roadmap reserves exception/recovery mechanics for S09.
- **Impact:** Due to this problem, a learner can memorize try/except as boilerplate around validation without understanding why the normal return path is skipped.
- **Proposed fix:** Either give a tightly bounded micro-model of raise/ValueError sufficient for function contracts and defer recovery patterns to S09, or use explicit result values in S05 and postpone try/except demonstrations.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F11 — The learner must understand a future data structure to see what the orchestrator returns and how composition preserves each helper's result.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** S05-T3-A paragraphs + composicion.py
- **Evidence:** The canonical composition example returns a dict from normalize_record, constructs a dict literal and uses that container as the core representation before S06 teaches dictionaries.
- **Impact:** Due to this problem, a learner can understand each helper separately but lose the composition model exactly when the outputs are packaged in unexplained dict syntax.
- **Proposed fix:** Demonstrate composition first with a simple returned string/value pair expressed separately; introduce record dictionaries only after S06 or provide a bounded explicit preview if the roadmap is revised.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F12 — The lesson conflates injecting a transformation strategy with injecting I/O and never shows how external reading/writing is supplied to or kept outside the pure core.
- **Category:** OUTCOME_NOT_TAUGHT
- **Location:** learning outcome 'inyectar I/O en el borde' + S05-T3-B
- **Evidence:** T3-B explains that I/O belongs at the boundary, but the promised injection example passes a normalizer function as norm=normalize_telefono and the callout calls that 'inyección'; it does not inject any input/output dependency.
- **Impact:** Due to this problem, a learner can finish S05 believing that passing any function argument counts as I/O injection and still hard-code open()/print() around business logic.
- **Proposed fix:** Either rename the outcome/topic to dependency injection if that is the intended skill, or show one tiny boundary function that receives an I/O callable while the normalizer remains pure.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F13 — The example intended to make f(f(x)) == f(x) visible hides the transformation behind new syntax and new text rules.
- **Category:** EXAMPLE_OVERLOADED_FUTURE_SYNTAX
- **Location:** S05-T3-B pureza_idem.py
- **Evidence:** The main idempotence example computes digits with ''.join(ch for ch in raw if ch.isdigit()), combining a generator expression and string-method semantics that have not been taught as usable concepts.
- **Impact:** Due to this problem, a learner may verify the printed equality but be unable to predict why the first normalization produced that value or whether applying it twice should remain stable.
- **Proposed fix:** Demonstrate idempotence first with a normalizer whose transformation is already transparent to the learner; move generator-expression/string-method implementation to the later text lesson.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F15 — The example claims configuration is captured by prefix but one major policy decision remains hidden and Peru-specific inside the closure.
- **Category:** TECHNICAL_CONTRADICTION
- **Location:** S05-T4-A closure/factory prose + legb_closure.py
- **Evidence:** The prose presents make_phone_normalizer(prefix) as country-configurable, but the inner function hard-codes startswith('51') and d[2:] regardless of the supplied prefix. Execution with make_phone_normalizer('+1') duplicates +1 for an already +1 input and strips a leading 51 even though +1 was requested.
- **Impact:** Due to this problem, a learner can believe the factory is generic by country when changing the prefix alone does not change its country-code stripping logic.
- **Proposed fix:** Use a closure example whose behavior depends only on the captured prefix, or pass the digits-to-strip/country policy explicitly as configuration too.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F17 — The worked example does not establish a pre-refactor green baseline and therefore cannot demonstrate that behavior was preserved across the change.
- **Category:** EXAMPLE_FAILS_TO_DEMONSTRATE_CLAIM
- **Location:** S05-T4-B refactor_seguro.py
- **Evidence:** The file defines normalize_email v1, defines _examples, then redefines normalize_email v2 and calls _examples only afterward. Python resolves the global normalize_email when _examples executes, so every assertion runs against v2; v1 is never tested in that run.
- **Impact:** Due to this problem, a learner can believe tests prove a refactor preserved behavior even when only the final implementation was ever exercised.
- **Proposed fix:** Run the same example assertions before redefining/refactoring the function and again afterward, or keep v1/v2 under distinct names and compare both against the same examples.
- **Sources (1):** audit/lessons-only/sections/S05.json

## P2 (11)

### S05-F04 — The real hazard is a mutable default that the function mutates; lists and dicts are examples, not the complete category. Mutable class instances can create the same problem.
- **Category:** TECHNICAL_OVERGENERALIZATION_BY_OMISSION
- **Location:** optional vocabulary + S05-T1-B paragraph 2
- **Evidence:** The rule is repeatedly phrased as 'nunca una lista o un diccionario' / 'nunca uses lista/dict mutable como default'.
- **Impact:** Due to this problem, a learner can conclude that a set or other mutable object is automatically safe merely because it is not a list or dict.
- **Proposed fix:** Say 'evita objetos mutables como listas o diccionarios cuando la función puede modificarlos; usa None y crea un objeto nuevo dentro'.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F05 — These are true facts but they are not needed for the T1-A outcome and introduce future collection/callback concepts before the basic call trace is stable.
- **Category:** COGNITIVE_LOAD_HIGH_PREMATURE_ADVANCED_DETAIL
- **Location:** S05-T1-A paragraph 3
- **Evidence:** Immediately after first defining call/return, the lesson introduces first-class functions, storing them in lists, returning functions and callbacks.
- **Impact:** Due to this problem, a learner can spend working memory on what a callback or function-as-value is instead of distinguishing definition, call and return.
- **Proposed fix:** Move first-class/callback material to T4-A when closures/factories are introduced, or to an optional note after the core function model.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F07 — Runtime behavior comes from code, but intended contract is not automatically whatever the current implementation happens to do. A mismatch is a defect that requires deciding which artifact is wrong.
- **Category:** CONTRACT_AUTHORITY_MISCONCEPTION
- **Location:** S05-T2-A callout Contrato legible
- **Evidence:** The callout says 'Si el docstring y el código discrepan, gana el código'.
- **Impact:** Due to this problem, a learner can silently rewrite documentation to match a buggy implementation instead of treating the discrepancy as evidence requiring resolution.
- **Proposed fix:** Replace with 'si discrepan, hay un defecto: ejecuta/consulta la especificación y corrige el artefacto que no representa la política acordada'.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F10 — Purity does not determine whether errors should be exceptions or result values, and a batch can catch per-record exceptions without aborting the whole batch.
- **Category:** DESIGN_RULE_OVERCLAIM
- **Location:** S05-T2-B callout ValueError vs. return
- **Evidence:** The callout prescribes 'raise para API internas puras; tupla u objeto de resultado cuando el lote no debe abortar'.
- **Impact:** Due to this problem, a learner can infer a false one-to-one rule between internal/pure functions and exceptions, then design inconsistent APIs when callers have different recovery needs.
- **Proposed fix:** State that either pattern can be valid; choose one explicit contract based on how callers must recover, and use it consistently within the module.
- **Sources (1):** audit/lessons-only/sections/S05.json

- **Evidence:** The callout introduces lambda syntax while the section's own function model and dependency-injection idea are still being learned.
- **Impact:** Due to this problem, a learner can treat lambda as required for testing/injection or confuse it with a fundamentally different kind of function.

### S05-F16 — The closure mechanism is buried under unrelated phone-normalization rules.

- **Impact:** Due to this problem, a learner can fail to identify which value is remembered by the closure because most visible lines are about text parsing rather than scope.

### S05-F18 — The strong earlier statement is broader than the evidence and is only corrected several paragraphs later.

- **Evidence:** The paragraph says that if asserts stay green, 'la conducta se preservó'. Paragraph 5 later correctly limits this by saying green proves only what the examples cover.
- **Impact:** Due to this problem, a learner can temporarily form the rule 'all green examples prove unchanged behavior', overlooking uncovered inputs or side effects.

### S05-F19 — The learner sees the delivery contract but not a complete learner-facing model of that contract inside theory.
- **Category:** PROMISE_EXAMPLE_INCOMPLETENESS
- **Location:** opening callout/optional criterion + T3-A canonical orchestrator
- **Evidence:** The lesson says closing S05 means four normalizers plus an orchestrator with docstring/hints/idempotence demonstrated, but theory's normalize_record combines only nombre/email and has no docstring; normalize_direccion is never implemented in a theory code block.
- **Impact:** Due to this problem, a learner can reach practice knowing the names of four policies but without a canonical example showing the full orchestrator boundary promised by the lesson.

### S05-F20 — Assert is shown as evidence for refactoring without delimiting it as a development/example mechanism rather than production validation.
- **Category:** TESTING_LIMIT_MISSING
- **Location:** S05-T4-B assert teaching
- **Evidence:** S05 promotes assert as executable examples but does not locally remind learners that Python -O removes assert statements; prior S03 testing knowledge was not credited as USABLE.
- **Impact:** Due to this problem, a learner can reuse assert as the only enforcement of a business precondition and assume it always executes.
- **Proposed fix:** Add a one-sentence boundary: asserts are development checks/examples and can be removed under python -O; do not use them as the only production validation of external input.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F21 — The learner is repeatedly asked to treat internal codes as meaningful nouns.
- **Category:** PERSISTENT_WIDOW_TERM_INTERNAL_ID
- **Location:** tagline, callouts, optional contract and multiple theory paragraphs
- **Evidence:** CP-N1-B and CASO-LIM-005 remain learner-facing internal identifiers without stable first-use expansion in plain language.
- **Impact:** Due to this problem, a learner can recognize the labels but not explain whether they denote a project, gate, dataset, exercise or software component.
- **Proposed fix:** Expand each at first use, e.g. 'CP-N1-B, el segundo incremento del proyecto acumulativo de Nivel 1' and 'CASO-LIM-005, el caso sintético de normalización de esta sección'.
- **Sources (1):** audit/lessons-only/sections/S05.json

### S05-F22 — A core relation is left for inference at the moment parameter passing is introduced.
- **Category:** MICRO_DEFINITION_MISSING_CORE_TERMINOLOGY
- **Location:** S05-T1-A/T1-B parameter and argument prose
- **Evidence:** The lesson uses placeholders params/args and then positional/keyword arguments, but never plainly distinguishes a parameter in the definition from an argument value supplied by a call.
- **Impact:** Due to this problem, a learner can use 'parameter' and 'argument' as interchangeable labels and form an unstable model of how call values bind to function-local names.
- **Proposed fix:** Add: 'parámetro = nombre declarado en def; argumento = valor que entregas al llamar; la llamada vincula cada argumento con un parámetro'.
