### S03-F01 — One of S03's promised T2 skills, guard clauses, inherently depends on function/return semantics that the roadmap withholds until S05, and the lesson does not teach that prerequisite before relying on 
- **Category:** ROADMAP_PREREQUISITE_CONFLICT_FUTURE_KNOWLEDGE_LEAK
- **Location:** opening definition of guard clause; T2-A; T2-B; T3-A; T3-B; T4-A; T4-B code
- **Evidence:** S03 defines a guard clause as an if at the start of a function that returns immediately and almost every nontrivial example defines a function, often with return and type annotations. V3 schedules function definition/call/return/parameters/type hints in S05.
- **Impact:** The learner can predict a comparison but cannot explain why return ends the route, why code below it is skipped, or why the function call produces the shown status; guard clauses become a copied shape rather than a control-flow model.
- **Proposed fix:** In S03 teach ordering/exclusivity/dead branches without early return, using top-level status assignments or direct prints. Move guard clauses/early return to S05 when functions and return are taught, or explicitly revise the roadmap if guard clauses must remain in S03.
- **Sources (1):** audit/lessons-only/sections/S03.json

### S03-F02 — Iteration is used as the presentation mechanism for the very evidence the novice is supposed to inspect, so it is not incidental syntax.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** T1-B, T2-A, T2-B, T3-A, T3-B, T4-A, T4-B code examples
- **Evidence:** Worked examples repeatedly use for loops to enumerate cases and outputs before V3 teaches for/range/iteration in S04.

### S03-F03 — Structured result containers become essential to understanding status/code/message and branch tests even though the section explicitly promises not to teach collections yet.
- **Category:** FUTURE_KNOWLEDGE_LEAK_SCOPE_CONTRADICTION
- **Location:** opening result-shape paragraph; optional contract; T2-B through T4-B code
- **Evidence:** The opening callout says collections arrive later, but learner-facing theory uses set literals, dict return values, lists of tuples, nested list/dict examples, indexing such as r["code"] and ex["value"], and a dict-of-examples representation before S06 teaches collections and unpacking.
- **Impact:** A novice can follow accept/reject/review in prose but lose the result once it becomes {status, code}, cannot explain brackets/indexing, and may conflate the rule being taught with the container syntax carrying it.
- **Proposed fix:** Keep S03 core results as simple strings or visually rendered tables. A small set used solely to demonstrate membership may remain with one microdefinition; defer dict/list/tuple protocols and indexing to S06.
- **Sources (1):** audit/lessons-only/sections/S03.json

### S03-F08 — An invariant is a condition required/intended to hold at a specified program or domain boundary; bugs or invalid external inputs can violate it. The current definition sounds like an automatically enf
- **Category:** FALSE_CORE_MENTAL_MODEL
- **Location:** opening paragraph 4 and T4-A invariant definition
- **Evidence:** The opening says 'un invariante es una promesa que el programa no puede romper' and gives 'el monto nunca es negativo' as an invariant, while the same section validates raw values that can in fact be negative and rejects them.
- **Impact:** The learner can conclude that once a statement is called an invariant, invalid values cannot exist, making validation/tests conceptually redundant and obscuring the difference between raw-input constraints and post-validation guarantees.
- **Proposed fix:** Define an invariant as 'una condición que declaras que debe cumplirse en una etapa concreta, por ejemplo después de validar; el código y las pruebas detectan cuando no se cumple'. Scope examples explicitly to raw vs accepted data.
- **Sources (1):** audit/lessons-only/sections/S03.json

- **Category:** OUTCOME_NOT_TAUGHT_EXAMPLE_MISSING

### S03-F10 — The same cause code receives two incompatible statuses in consecutive subtopics with no different domain contract to explain the change.
- **Category:** POLICY_DEFINITION_DRIFT_TECHNICAL_CONTRADICTION
- **Location:** T3-A regla_region_edad.py versus T3-B codigo_a_status.py
- **Evidence:** T3-A explicitly classifies a region outside the allowlist as review and prints R-FUERA 30 -> review. T3-B then maps the stable code NOT_IN_ALLOWLIST to reject without announcing a policy change, even though it says it is scaling the T3-A motor.

### S03-F12 — S03 violates the exact edge case its previous lesson warned about, turning booleans into ages.
- **Category:** TECHNICAL_CONTRADICTION_BACKWARD_REFERENCE_DEFECT
- **Location:** T2-B validate_edad and T4-B validate_edad_msg
- **Evidence:** Both validators use isinstance(edad, int) without excluding bool. S02 explicitly taught that bool is a subtype of int and that business integer validators should use isinstance(x, int) and not isinstance(x, bool). Executing the S03 logic confirms True/False pass the int check; validate_edad_msg(True) returns OK.
- **Impact:** The learner can submit True as edad and receive accept/OK in T4-B, learning that the validator is type-safe when it is not.
- **Proposed fix:** For domain integer fields where bool is invalid, use if not isinstance(edad, int) or isinstance(edad, bool): BAD_TYPE, and add True/False branch cases.
- **Sources (1):** audit/lessons-only/sections/S03.json

### S03-F13 — The lesson offers two incompatible minimum coverage contracts; the weaker one can miss an entire branch while appearing to satisfy all three statuses.
- **Category:** TECHNICAL_CONTRADICTION_TEST_COVERAGE
- **Location:** T4-A paragraph 2 versus T4-B paragraph 2 and learning outcome 8
- **Evidence:** T4-A says the professional minimum is at least one example per decision state, but T4-B correctly says one test per branch and gives four paths (None, wrong type, range, OK). Multiple branches can share the same reject state, so one reject example cannot cover them all.
- **Impact:** A validator with two reject causes can be tested with only one reject input, leaving the other branch broken while the learner believes the minimum has been met.
- **Proposed fix:** Change T4-A to 'at least one example per distinct branch; if several branches share a status, each still needs a case'. Keep accept/reject/review coverage as a secondary check.
- **Sources (1):** audit/lessons-only/sections/S03.json

- **Location:** T1-B short-circuit paragraph and truthiness_monto.py
