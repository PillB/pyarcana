## P1 (12)

### S09-F03 — Two incompatible direction models are given for the same artifact.
- **Category:** FALSE_CORE_MENTAL_MODEL_TRACEBACK
- **Location:** opening paragraph 3 + T2-A paragraph 1
- **Evidence:** The opening says read a trace bottom-up; T2-A says frames are 'del más reciente al más profundo (o viceversa según la herramienta)'. The standard Python traceback prints the call chain and ends with the innermost failing frame followed by exception type/value.
- **Impact:** The learner cannot distinguish caller frames from the frame where the exception arose and may start debugging the wrong layer.
- **Proposed fix:** Teach one concrete standard-Python trace: top frame = earlier caller, later frames = deeper calls, last frame = immediate failure location, final line = exception class/message; mention alternative tool presentations only after that model is stable.
- **Sources (1):** audit/lessons-only/sections/S09.json

### S09-F04 — The first formal exception lesson hides raise/chaining behind future OOP syntax.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** T1-A custom exception code
- **Evidence:** class ValidationError(Exception) and class ParseError(Exception) introduce class definition and inheritance, while the V3 roadmap first teaches classes/instances in S11.
- **Impact:** The learner can copy a custom exception declaration without understanding class, base class, inheritance or why Exception appears in parentheses.
- **Proposed fix:** Teach raise/chaining first with built-in exceptions. If custom exceptions are indispensable, add a bounded microdefinition that this one-line class creates a named exception subtype, then defer general class semantics to S11.
- **Sources (1):** audit/lessons-only/sections/S09.json

### S09-F06 — The diagram assigns a false point-of-no-return to row recovery.

### S09-F08 — The lesson repeats print-theater: an error label is shown while the operating system sees normal success.
- **Category:** FAIL_FAST_EXIT_STATUS_CONTRADICTION
- **Location:** T1-B boundaries.py + T4-A failfast_quarantine.py
- **Evidence:** Both examples label configuration errors fatal/abort but catch RuntimeError at the outer demo boundary and merely print it. Executed as standalone Python processes, both terminated with return code 0.
- **Impact:** The learner believes 'fatal:' or 'abort:' on stdout/stderr is equivalent to a failing job status, so schedulers/CI can treat failed jobs as success.
- **Proposed fix:** For the fatal demonstration, let the exception escape the process or re-raise after logging. Explicit exit-code mapping belongs at the S10 CLI boundary, but S09 must not claim a caught-and-swallowed demo is fail-fast.
- **Sources (1):** audit/lessons-only/sections/S09.json

### S09-F09 — The visual teaches two false causal rules and contradicts T1-A.
- **Category:** FIGURE_TECHNICAL_FALSEHOOD
- **Location:** S09-error-boundary figure
- **Evidence:** Caption: 'Atrapar Exception en el origen borra el tipo; atraparlo todo en la frontera pierde el contexto de dónde ocurrió.' - **Proposed fix:** Caption should say broad catches can mix policies; swallowing/replacing without chaining loses evidence. Catching at a process boundary can be appropriate when the original exception/traceback is preserved and the error is re-raised or mapped deliberately.

### S09-F10 — The redaction policy sanitizes one message channel but not exception text carried by traceback/log.exception.
- **Category:** PRIVACY_CONTRADICTION_EXCEPTION_TEXT
- **Location:** T1-A + T2-A + T3-B
- **Evidence:** T1-A encourages including the problematic raw value in exception messages. T2-A proposes traceback.format_exc; T3-B says mask the explicit log message then use log.exception. Python log.exception attaches exception information/traceback, including the exception message. Execution confirmed a full email in ValueError reappeared below a masked logging message.
- **Impact:** The learner logs 'email=a***@...' and assumes the event is safe while the traceback contains 'ValueError: email completo: ana.rojas@...'.
- **Proposed fix:** Prohibit sensitive raw values in exception messages that may be logged; store safe identifiers/reason codes, and ensure any full diagnostic data remains in separately protected evidence. Teach that log.exception includes the exception message as well as stack frames.
- **Sources (1):** audit/lessons-only/sections/S09.json

### S09-F12 — Essential debugging workflow is externalized to later practice despite being a core S09 outcome.

### S09-F20 — Identity of an operation is confused with enforcement of idempotent behavior.
- **Category:** FALSE_IDEMPOTENCY_MENTAL_MODEL
- **Location:** T4-B paragraph 2 + callout
- **Evidence:** The lesson says operations are idempotent when they use the same write key and suggests (source, record_id, version)+payload hash. A key alone does not prevent duplicate side effects; the receiving persistence/action must enforce uniqueness, overwrite/upsert semantics, or remember processed keys.
- **Impact:** The learner adds an idempotency key to a normal INSERT but still performs two inserts on retry and believes the system is safe.
- **Proposed fix:** Define idempotency behavior first: repeating the same logical request has the same externally observable result. Then explain an idempotency key is one mechanism only when the receiver actually uses it to detect/reuse a prior result or perform an upsert.
- **Sources (1):** audit/lessons-only/sections/S09.json

### S09-F21 — The safety condition for retries exists only in prose, while executable code teaches retrying any callable that raises TimeoutError.
- **Category:** OUTCOME_NOT_TAUGHT_RETRY_IDEMPOTENCE
- **Location:** T4-B retry_policy.py
- **Evidence:** The code retries an arbitrary callback fn and demonstrates only a counter; it neither performs nor protects a side effect. It therefore cannot demonstrate the idempotency requirement named in the outcome. The example also depends on passing functions as values, a concept not safely mastered from S05.
- **Impact:** The learner copies fetch_with_retry around state-changing operations without a deduplication/upsert contract.
- **Proposed fix:** First demonstrate retry around a side-effect-free read, explicitly saying why it is safe. Then show a tiny fake store that rejects/reuses an already-seen idempotency key before claiming safe retry of writes.
- **Sources (1):** audit/lessons-only/sections/S09.json
