## P1 (9)

### S04-F03 — The prose confuses asymptotic linear complexity with a one-pass-only design rule.
- **Category:** TECHNICAL_OVERCLAIM_COMPLEXITY_MODEL
- **Location:** opening theory paragraph 4
- **Evidence:** The lesson says one pass is enough and that needing two passes probably means information was stored incorrectly. Two sequential passes over n items perform about 2n work and remain O(n); multiple passes can be clearer or intentionally separate concerns.
- **Impact:** A learner can reject a clear two-pass O(n) solution as algorithmically wrong or contort code into one pass merely to satisfy a false performance rule.
- **Proposed fix:** State that one pass is often sufficient for these counters, but a small fixed number of passes is still O(n); avoid repeated nested rescans when they are unnecessary.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F04 — S04 must iterate over something, but the lesson goes far beyond a bounded iterable preview and makes S06 structures necessary to understand the loop examples.
- **Category:** FUTURE_KNOWLEDGE_LEAK_COLLECTIONS
- **Location:** T1-A, T1-B, T2-A, T3-A, T3-B, T4-A and T4-B code
- **Evidence:** Core examples use list literals, lists of dictionaries, dictionary indexing, append, slicing, lists of tuples, set/dict literals, nested structures and indexing even though V3 teaches lists/tuples/dicts/sets/slicing/unpacking formally in S06.
- **Impact:** The learner spends attention decoding brackets, keys, append, slicing and nested records instead of predicting how for/while changes state.
- **Proposed fix:** Introduce one simple list as an ordered group of values for the sole purpose of iteration, use flat strings/integers in core examples, and defer nested dict/list operations, slicing and structure choice to S06.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F05 — Unearned syntax is used to explain core S04 outcomes even where Python 3.12 already provides zip(..., strict=True) and where an exception handler is not required to teach an invalid index.
- **Category:** FUTURE_KNOWLEDGE_LEAK_FUNCTIONS_EXCEPTIONS
- **Location:** T1-B zip_strict; T2-B clean_lines; T4-B try/except
- **Evidence:** The lesson defines helper functions with parameters/return, raises ValueError and catches ValueError/IndexError using try/except before S05 teaches functions/return and S09 teaches exceptions.
- **Impact:** The learner can understand the loop idea yet be unable to trace why a helper returns, why raise transfers control, or why except runs.
- **Proposed fix:** Use top-level loop examples; use zip(..., strict=True) directly; describe the mismatch ValueError without teaching a custom function/handler; move formal reusable helpers to S05 and exception recovery to S09.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F07 — The first rule incorrectly makes 'condition becomes false' the only valid termination mechanism, then the next subtopic contradicts it with break.
- **Category:** INTERNAL_TECHNICAL_CONTRADICTION
- **Location:** T2-A paragraph 2 vs T2-B paragraph 3
- **Evidence:** T2-A says a while loop must update state each turn and becomes infinite if the condition never becomes false. T2-B later says while True is legitimate when a reachable break terminates it.
- **Impact:** The learner cannot form one stable rule for proving termination and may incorrectly treat every while True as invalid or believe break somehow changes the truth value of True.
- **Proposed fix:** Teach one model: a loop needs a reachable exit path—normally the condition eventually becomes false, or a break/return/exception exits it. In S04 core, emphasize condition progress first and introduce break explicitly afterward.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F08 — The worked example does not demonstrate the safeguard it claims to teach.
- **Category:** EXAMPLE_DOES_NOT_TEACH_OUTCOME
- **Location:** T2-B break_continue.py
- **Evidence:** The section promises safeguards against infinite loops and recommends MAX iterations, but its code uses a finite for loop. max_n limits len(kept), not iteration count; if every line is SKIP/blank, the loop can execute every input item regardless of max_n. Execution with 1000 SKIP rows and max_n=2 performs 1000 iterations.
- **Impact:** The learner can copy max_n believing it is an iteration safety cap when it only caps accepted items.
- **Proposed fix:** Demonstrate a while loop with an explicit iters counter and condition such as while i < len(lines) and iters < MAX_ITERS, then separately demonstrate break/continue on a finite for.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F10 — The callout contradicts the central contract of the entire lesson.
- **Category:** TECHNICAL_CONTRADICTION_DENOMINATOR
- **Location:** opening paragraphs + T3-A paragraph/callout
- **Evidence:** The opening makes attempted rows the denominator and explains why processed rows can bias the rate. T3-A prose repeats attempted rows, but its callout says 'Tasa de error = errores / procesados'.
- **Impact:** The learner receives two formulas for the same metric and cannot know which denominator to implement when early failures exist.
- **Proposed fix:** Change the callout to 'errores / registros intentados' and define attempted/processed once if the course needs both terms.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F12 — The roadmap asks for readable comprehensions, but the example makes three different container kinds and nested record access prerequisites to reading the syntax.
- **Category:** EXAMPLE_OVERLOADED_FUTURE_COLLECTIONS
- **Location:** T3-B comprehensions_resumen.py
- **Evidence:** The first comprehension example simultaneously uses a list of dictionaries, dictionary indexing, a list comprehension, set comprehension, dict comprehension, sorted(), and later dict lookup. S06 has not yet taught those structures.
- **Impact:** A learner cannot tell which parts constitute the comprehension versus which parts are dictionary/set syntax, so the intended compact loop/filter transformation remains opaque.
- **Proposed fix:** Teach one list comprehension over a simple flat list first, e.g. positivos = [m for m in montos if m > 0]. Defer dict/set comprehensions and nested records to S06.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F13 — A known-bad prior mental model is imported into debugging as though mastered.
- **Category:** FORGOTTEN_PREREQUISITE_DEFINITION_DRIFT
- **Location:** T4-A paragraph 1
- **Evidence:** The trace paragraph tells the learner to locate the first frame that 'rompe el invariante'. The effective S03 ledger marks invariant MISCONCEPTION_RISK because S03 defined it as something the program cannot break. S04 does not repair the term before depending on it.
- **Impact:** The learner can wonder how a trace can ever show an invariant being broken if an invariant was defined as something the program cannot break.
- **Proposed fix:** At first reuse say 'la condición que esperabas conservar (el invariante)' and explicitly note that a bug can violate it; the trace helps find the first violation.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F15 — The wrong operation is blamed for the exception.
- **Category:** TECHNICAL_FALSEHOOD
- **Location:** T4-B paragraph 2
- **Evidence:** The lesson says 'range(len(xs)+1) explota con IndexError'. range(len(xs)+1) is valid and yields 0 through len(xs); IndexError occurs only when that last index is used to access xs[len(xs)].
- **Impact:** The learner can expect constructing/iterating the range itself to fail and cannot localize an IndexError to sequence access.
- **Proposed fix:** Say 'si usas for i in range(len(xs)+1) para acceder xs[i], la última vuelta intenta xs[len(xs)] y ese acceso lanza IndexError'.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F01 — The learner-facing identity uses an ambiguous domain adjective and internal/English labels instead of stating the actual skill: iterating over batches and producing reliable summaries.
- **Category:** WIDOW_TERM_PROMISE_AMBIGUITY
- **Location:** title + tagline

- **Impact:** A learner can expect database transaction semantics or a finance-only lesson and cannot infer what CP-N1-A denotes.
- **Proposed fix:** Prefer 'Iteración y resúmenes por lote' and expand CP-N1-A once in plain language; translate or microdefine comprehension at first meaningful use.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F02 — The contrast conflates 'one program execution for many records' with 'not processing records one at a time'.
- **Category:** MECHANISM_INACCURACY
- **Location:** jobRelevance
- **Evidence:** A batch processor is defined as a program that 'recorre muchos registros en un solo pase, no uno por uno'. A normal for loop over a batch still handles successive records one by one inside one execution/pass.
- **Impact:** The learner can infer that batch processing implies simultaneous processing and later misclassify a sequential loop as not being batch processing.
- **Proposed fix:** Say that batch processing handles many records in one execution, usually visiting them successively inside a loop.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F06 — A fallback for unsupported course runtimes creates extra functions/exceptions and reopens version ambiguity.
- **Category:** RUNTIME_CONTRACT_DRIFT_UNNECESSARY_FALLBACK
- **Location:** T1-B prose/code/callout
- **Evidence:** S04 repeatedly frames strict zip as Python 3.10+ and supplies a manual compatibility helper although the course runtime is intended to be Python 3.12.
- **Impact:** The learner can infer that the course expects multiple unsupported Python versions and cannot tell whether to use the built-in strict option or the helper.
- **Proposed fix:** Assume the canonical Python 3.12 runtime and teach zip(..., strict=True) directly; remove the compatibility helper from core theory.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F09 — A common risk is turned into an absolute hardware claim.
- **Category:** TECHNICAL_OVERCLAIM
- **Location:** T2-B callout
- **Evidence:** The callout states that an infinite loop in production 'agota CPU y bloquea el lote'. Infinite loops can block progress and consume resources, but a loop that sleeps or waits for I/O does not necessarily exhaust CPU.
- **Impact:** The learner can use CPU saturation as a diagnostic criterion for infinite loops and miss loops that are stuck while waiting or sleeping.
- **Proposed fix:** Say an unintended infinite loop can prevent progress and may consume CPU or other resources depending on what its body does.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F11 — A new decision syntax is embedded in the line whose denominator behavior is supposed to be the learning focus.

### S04-F14 — A trace mismatch can originate in the branch condition, validator output, test data, state update, display code or counter. The evidence given does not isolate one cause.
- **Category:** DEBUGGING_CAUSAL_OVERCLAIM
- **Location:** T4-A paragraphs 2-3
- **Evidence:** The prose says that if a trace does not match the print, the bug is in state update, and if it does not match the summary the bug is in the counter, not the S03 validator.
- **Impact:** The learner can stop investigating the validator or condition because the lesson told them the counter must be at fault.
- **Proposed fix:** Use the trace to locate the first divergent state, then inspect the condition/update that produced that divergence; do not predeclare which component is innocent.
- **Sources (1):** audit/lessons-only/sections/S04.json

### S04-F16 — The term is stretched from index/count mistakes to every inclusive/exclusive policy error.
- **Category:** TERMINOLOGY_DRIFT
- **Location:** T4-B paragraph 2
- **Evidence:** The lesson labels >= versus > in business thresholds as 'off-by-one de negocio'. This is a boundary/inclusivity error; it is only literally off-by-one for discrete integer boundaries where the threshold differs by one accepted value.
- **Impact:** The learner can call any boundary-policy mistake off-by-one and lose the useful distinction between indexing errors and business-rule boundary errors.
- **Proposed fix:** Call >= versus > a 'boundary/inclusivity error'; then note that for integer counts it can resemble an off-by-one error.
- **Sources (1):** audit/lessons-only/sections/S04.json
