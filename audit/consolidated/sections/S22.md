## P1 (17)

### S22-F01 — UNTRUSTED_S21_PACKAGE_ASSUMED_RECONCILED
- **Evidence:** S22 repeatedly says the S21 report package is already reconciled and uses its run data as input.
- **Impact:** S21 remains REPAIR_REQUIRED; its parity/provenance/pending_review evidence is not creditable. S22 can therefore package or route an unverified report.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F02 — ROUTABLE_EXAMPLE_PE_USED_AS_LAB_EMAIL_DOMAIN
- **Evidence:** The lab allowlists and addresses use @example.pe and explicitly say it is not an impossible-to-route domain.
- **Impact:** RFC/IANA reserve .test/.example/.invalid and example.com/net/org, not example.pe. A future provider adapter could accidentally address a real domain, contradicting the no-real-email gate.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F04 — BCC_PRIVACY_MODEL_INCOMPLETE_FOR_EXTERNAL_RECIPIENTS
- **Evidence:** The section treats moving externals to BCC as a privacy protection for the recipient list.
- **Impact:** BCC hides BCC addresses from other recipients, but BCC recipients normally still receive visible To/Cc headers. Individual sends are required when an external must not learn internal recipient addresses.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F08 — SANITIZER_ALLOWED_HOSTS_PARAMETER_BYPASSED_BY_HARDCODED_SUFFIX
- **Evidence:** sanitize_html accepts allowed_hosts but also always permits host.endswith('.example.pe').
- **Impact:** Passing allowed_hosts={'corp.pe'} still permits sub.example.pe. The security parameter does not actually define the policy.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F10 — DRAFT_ONLY_LEAST_PRIVILEGE_CHECK_ACCEPTS_SEND
- **Evidence:** least_privilege_ok treats mail.send as part of the allowed capability set and only excludes mail.full.
- **Impact:** A granted ['mail.draft','mail.send'] evaluates True even though the callout says deny mail.send for a draft-only lab.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F11 — SCOPE_POLICY_IS_HARDCODED_NOT_OBSERVED
- **Evidence:** Prose says requested∩allowed and granted scopes are audited, but the example hardcodes requested_scopes/granted_scopes and never validates a provider response or fail-closes on missing/unexpected grants.
- **Impact:** Learners can print least_privilege_ok without demonstrating that authorization actually matches policy.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F12 — DRAFT_EXPIRY_NOT_INTEGRATED_WITH_APPROVAL_STATE
- **Evidence:** T2-B says expired drafts cannot be promoted without regeneration/reapproval; T4 approval state machine never checks draft expiry or draft usability.
- **Impact:** An approval can remain 'approved' after the underlying draft expires or changes.

### S22-F16 — DEDUPE_OVERWRITES_FIRST_RECIPIENT_ROLE
- **Evidence:** T3-B promises dedupe preserving first appearance, but OrderedDict assignment replaces the value for a duplicate email.
- **Impact:** A later duplicate can change a first BCC entry into To/CC and increase disclosure while preserving the original position.

### S22-F17 — EXTERNAL_RECIPIENT_POLICY_HARDCODED_TO_OTHER_TEST
- **Evidence:** T3-B says every external domain is forced to BCC, but code only checks email.endswith('@other.test').
- **Impact:** Any other external domain remains visible, so the policy does not generalize beyond the fixture.

### S22-F19 — APPROVER_ROLE_NOT_AUTHORIZED
- **Evidence:** approval_sm.py accepts any actor string for approve.
- **Impact:** The same analyst who submitted can call approve and reach approved. 'Human approval' is not equivalent to an authorized independent reviewer.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F20 — APPROVAL_AUDIT_MISSING_TIMESTAMP_AND_COMMENTS
- **Evidence:** The transition log stores from/to/action/actor only.
- **Impact:** S21 carry-forward and S22 prose require actor, timestamp and review comments/notes; these are necessary to reconstruct who approved what and when.

### S22-F21 — APPROVAL_NOT_BOUND_TO_EXACT_DRAFT_CONTENT
- **Evidence:** Approval transitions contain no draft_id, message hash, recipient set, subject, attachment hashes or body version.
- **Impact:** A message can be edited after approval without invalidating the approval record. Human review must bind to the exact bytes/payload reviewed.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F22 — EVERY_RECIPIENT_CONFIRMATION_GATE_NOT_IMPLEMENTED
- **Evidence:** Tagline says every recipient requires confirmation, but the state machine approves one draft state with no per-recipient confirmation evidence.
- **Impact:** A multi-recipient draft can be approved without showing that each To/Cc/Bcc address was reviewed.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F23 — IDEMPOTENCY_KEY_OMITS_MESSAGE_PAYLOAD_FIELDS
- **Evidence:** Key is sha256(run_id\|to\|body_ver)[:16].
- **Impact:** Subject, body content hash, Cc/Bcc, attachments, sender and recipient-set version are absent; changed content can reuse an old draft if body_ver is not manually bumped.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F24 — TRUNCATED_NONATOMIC_KEY_CANNOT_GUARANTEE_IDEMPOTENCY
- **Evidence:** Outcome says 'Garantizar idempotencia' using sha256[:16] and a normal dict check-then-insert.
- **Impact:** Sixteen hex characters are a 64-bit prefix and there is no collision check or atomic uniqueness. Concurrent workers can also race through the membership check.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F25 — IDEMPOTENCY_AUDIT_LOG_LACKS_ACTOR_TIMESTAMP_AND_STATE
- **Evidence:** T4-B says audit log records create/submit/approve/retry_hit with actor and timestamps in production; example only logs create/retry_hit with key/draft_id.
- **Impact:** The final idempotency example does not satisfy its own audit-log outcome or connect to the approval log.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F26 — NO_INTEGRATED_PERSISTED_DRAFT_APPROVAL_WORKFLOW
- **Evidence:** Theory examples separately demonstrate MIME, sanitizer, scopes, draft store, recipients, list hygiene, approval and key.
- **Impact:** No executable flow consumes a validated S21 manifest, creates a persisted .eml/sandbox draft, binds verified recipients, submits it, records approval, checks expiry/idempotency and persists one audit trail. The section gate is therefore not demonstrated end-to-end.
- **Sources (1):** audit/lessons-only/sections/S22.json

## P2 (11)

### S22-F03 — EMAIL_IRREVERSIBILITY_OVERCLAIM
- **Evidence:** Opening says an email 'no se puede deshacer'.
- **Impact:** Recall/retraction mechanisms exist in limited systems; the transferable rule is that delivery cannot be reliably revoked once a recipient/provider has received the message.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F05 — ATTACHMENT_DESCRIBED_AS_CONTROLLED_DISCLOSURE_SURFACE
- **Evidence:** T3-B suggests sensitive detail can live in a 'controlled attachment' instead of the body.
- **Impact:** An email attachment is copied to the recipient and can be forwarded; it is not equivalent to an access-controlled portal. Disclosure minimization must cover attachments too.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F06 — MIME_HEADER_COUNT_FALSE_GREEN
- **Evidence:** T1-A says counting Content-Type headers validates that the multipart tree is correctly nested.
- **Impact:** The number of Content-Type headers does not prove multipart/alternative placement, attachment disposition, or part semantics; different trees can have the same count.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F07 — PLAIN_TEXT_PRESENTED_AS_PROTOCOL_MANDATORY
- **Evidence:** Figure/callout say the plain-text part is 'not optional' and many clients/filters require it.
- **Impact:** multipart/alternative text+HTML is strong compatibility practice, but an HTML-only MIME message is not categorically invalid. Teach it as a robustness/accessibility requirement of the course, not a universal protocol law.
- **Sources (1):** audit/lessons-only/sections/S22.json

### S22-F09 — RELATIVE_LINK_POLICY_CONTRADICTS_IMPLEMENTATION
- **Evidence:** T1-B says relative routes are allowed, but sanitize_html only permits URLs matching ^https?://.
