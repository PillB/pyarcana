### S14-F02 — Debido a este problema, un alumno razonable puede formar la regla falsa 'mezclar tipos hace que ndarray deje de ser homogéneo o NumPy vuelva…
- **Category:** FALSE_MENTAL_MODEL_MIXED_DTYPE
- **Location:** opening p2
- **Evidence:** La analogía dice que si mezclas textos y números 'se pierde la ventaja y vuelves a contar monedas'. NumPy intenta encontrar un dtype común: por ejemplo int+float puede convertirse a float y seguir operando vectorizadamente; int+texto puede convertirse a Unicode; mezclas con None pueden terminar en object y perder muchas ventajas numéricas.
- **Impact:** Debido a este problema, un alumno razonable puede formar la regla falsa 'mezclar tipos hace que ndarray deje de ser homogéneo o NumPy vuelva automáticamente a un loop Python'.
- **Proposed fix:** Explicar coerción a dtype común y distinguir dtype numérico común de string/object, donde operaciones numéricas pueden cambiar o dejar de estar disponibles.

### S14-F14 — Debido a este problema, un alumno puede escoger rtol/atol como múltiplos arbitrarios de eps y declarar equivalentes resultados que incumplen…
- **Category:** NUMERICAL_TOLERANCE_MISCONCEPTION
- **Location:** S14-T3-B p2
- **Evidence:** El texto define correctamente finfo(float).eps como separación alrededor de 1.0, pero añade que esa escala 'es lo que necesitas para elegir la tolerancia de un allclose'. eps no determina por sí solo el error aceptable de un algoritmo ni la tolerancia de negocio; el espaciado cambia con la magnitud y el error acumulado depende de operaciones/condicionamiento.
- **Impact:** Debido a este problema, un alumno puede escoger rtol/atol como múltiplos arbitrarios de eps y declarar equivalentes resultados que incumplen la precisión requerida o rechazar resultados correctos a otra escala.
- **Proposed fix:** Separar machine epsilon de error budget: eps ilustra resolución cerca de 1; rtol/atol se justifican con escala, algoritmo y tolerancia del dominio.
- **Sources (1):** audit/lessons-only/sections/S14.json

### S14-F17 — Debido a este problema, un alumno puede creer que ha implementado un guard de memoria cuando en realidad comprueba el presupuesto después de…
- **Category:** MEMORY_GUARD_AFTER_ALLOCATION
- **Location:** S14-T4-B p1
- **Evidence:** El presupuesto se expresa como pair.nbytes <= max_bytes, que solo puede consultarse después de materializar la matriz n×n. Con n grande, la asignación puede agotar RAM antes de que exista pair para comprobar nbytes.

### S14-F18 — Debido a este problema, una implementación vectorizada puede devolver una forma equivocada y aun pasar el test de equivalencia numérica.
- **Category:** ALLCLOSE_SHAPE_CONTRACT_LOSS
- **Location:** S14-T4-B p2-p3 + allclose_mem.py
- **Evidence:** La sección trata shape como parte del contrato pero propone allclose como oráculo de equivalencia sin exigir shape igual. NumPy allclose aplica broadcasting, por lo que arrays de shapes diferentes pueden devolver True si sus valores broadcastados son cercanos.

- **Proposed fix:** Primero exigir a.shape == b.shape (y shape esperado); después aplicar assert_allclose a los valores.

### S14-F19 — Debido a este problema, dos implementaciones semánticamente equivalentes respecto a faltantes pueden fallar, o un alumno puede activar equal…
- **Category:** ALLCLOSE_NONFINITE_POLICY_MISSING
- **Location:** S14-T3-B -> S14-T4-B
- **Evidence:** T3-B admite NaN/inf como edge cases, pero T4-B no define cómo entran al contrato de equivalencia. allclose considera NaN distinto por defecto salvo equal_nan=True y trata inf por posición/signo. Usar equal_nan=True sin política también puede ocultar errores.

- **Proposed fix:** Comparar primero máscaras de no-finitos según política; luego comparar valores finitos. Usar equal_nan=True solo si el contrato declara que NaN en la misma posición representa el mismo estado.
