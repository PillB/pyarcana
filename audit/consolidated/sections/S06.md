## P1 (10)

### S06-F03 🚩 — The outer container versus inner-object boundary is not kept explicit across slicing, list.copy and dict unpacking.
- **Category:** MISCONCEPTION_RISK_SHALLOW_COPY
- **Location:** T1-A slicing + T1-B shallow copy + T2-A dict merge
- **Evidence:** T1-A says a slice creates a new list; T1-B narrows shallow-copy risk to tags/contacts/'campos anidados'; T2-A says {**base, **override} preserves the original. In all three cases nested row/config objects can remain shared.
- **Impact:** A learner can mutate ventana[0]['region'] or merged['opts']['retry'] and expect the source structure to remain independent, but the source changes because the inner dict is shared.
- **Proposed fix:** State that slicing/list.copy/dict-unpacking create a new outer container but normally reuse references to nested objects; show one top-level row-field mutation through the copy.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F04 🚩 — The canonical first slicing worked example depends on an error-signalling mechanism the learner cannot yet explain.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** T1-A last_n code
- **Evidence:** The first slicing example actively uses 'raise ValueError' even though exceptions/raise remain MENTION_ONLY and the roadmap reserves exception mechanics for S09.
- **Impact:** The learner can copy 'raise ValueError' as a ritual but cannot predict where control goes, why the function stops or how a caller sees that failure.
- **Proposed fix:** Keep T1-A focused on valid n values; describe n>=0 as a precondition, or add an explicit bounded micro-definition of raise before using it and defer catching to S09.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F06 🚩 — Arity validation is presented as if it also validates semantic column meaning.
- **Category:** TECHNICAL_CONTRADICTION
- **Location:** T1-B paragraph 1
- **Evidence:** The paragraph first correctly says Python only checks the number of unpacked elements and that swapped region/monto values unpack without error, then says the ValueError for wrong arity 'impide que una región termine silenciosamente en la variable del monto'.
- **Impact:** A learner can believe successful unpacking proves that each position contains the intended kind of field, even though ('C001', 10, 'Lima') binds 10 to region and 'Lima' to monto without error.
- **Proposed fix:** Replace the final claim: ValueError detects wrong element count, not swapped semantics; semantic validation needs a separate contract/check.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F11 🚩 — Flattening is described as representation-only even though it can change what information is recoverable.
- **Category:** TECHNICAL_OVERCLAIM_INFORMATION_LOSS
- **Location:** T3-A paragraph 2 + flatten_txs
- **Evidence:** The prose says 'Aplanar cambia la vista, no la verdad'. The one-row-per-transaction flattening drops a client entirely when that client has zero transactions unless another representation preserves that parent row.
- **Impact:** A learner can export only the flattened transaction table and later assume it still proves that a zero-transaction client existed; that client has disappeared from the rows.
- **Proposed fix:** Say flattening changes representation and can lose parent-level facts unless they are repeated or retained separately; explicitly mention clients with zero transactions.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F12 🚩 — The helper's default interface does not preserve the exact distinction the prose says it centralizes.
- **Category:** TECHNICAL_CONTRADICTION_MISSING_SENTINEL
- **Location:** T3-B prose + get_nested code
- **Evidence:** The subtopic's purpose is to distinguish missing from present-empty/present-None, but get_nested defaults to None and the example uses the ordinary string 'MISSING' as sentinel. A present value None is indistinguishable from missing when default is omitted, and a real value 'MISSING' is indistinguishable from missing when that string is used as default.
- **Impact:** The learner can report a present value as absent or fail to tell a missing key from a legitimate string equal to the chosen sentinel.
- **Proposed fix:** Use a unique private sentinel object (e.g. MISSING = object()) and explain identity checking, or return a separate found/value pair; do not make None the default when None is a legitimate present value.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F13 🚩 — The canonical safe-access example depends on a new function-signature mechanism with a different meaning for * from the one just shown in S05.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** T3-B get_nested signature
- **Evidence:** def get_nested(d, *keys, default=None) uses variadic positional parameter collection (*keys). S05 introduced '*' only as the keyword-only separator, not *args collection semantics.
- **Impact:** The learner can misread *keys as the S05 keyword-only separator or be unable to explain why multiple key arguments become one iterable inside the function.
- **Proposed fix:** Accept a single path sequence: get_nested(d, keys, default=...) and call it with ('profile','phone'); teach *args later.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F15 🚩 — The outcome 'sorted(..., key=)' is taught through a different function-definition syntax that the learner cannot yet explain.
- **Category:** PREREQUISITE_LEAK_LAMBDA
- **Location:** T4-A sorted_key.py
- **Evidence:** Both canonical sorting helpers use lambda as the key function. Lambda was only mentioned incidentally in S05 and never gained a usable model.
- **Impact:** The learner can memorize 'key=lambda r:' without understanding that key receives one record and must return the comparison value.
- **Proposed fix:** Use named key functions first: def region_name(r): return (r['region'], r['nombre']); pass key=region_name. Lambda can be an optional compact form later.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F17 🚩 — The example compresses the relationship traversal precisely when the learner needs to see parent->child traversal step by step.

- **Evidence:** The first nested-structure flatten example uses a list comprehension with two for clauses and dict construction in the output expression. S04 comprehensions remained PARTIAL and nested comprehensions were not taught.
- **Impact:** The learner may reproduce the flat output while being unable to trace which client owns each transaction or why zero-child parents disappear.
- **Proposed fix:** Use explicit nested for loops and append first; only show the comprehension after the traversal model is stable.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F18 🚩 — A future data format becomes a core S06 outcome without defining what JSON represents, which Python values map to it or what serialization means.
- **Category:** FUTURE_KNOWLEDGE_LEAK_ROADMAP_SCOPE_DRIFT
- **Location:** learning outcome + opening + T4-B
- **Evidence:** S06 promises 'producir JSON determinista' and imports/serializes JSON, while roadmap V3 places files/CSV/JSON in S08 and ZERO_TECH does not know JSON. S06 itself says S08 will connect the model to CSV and JSON.
- **Impact:** The learner can copy json.dumps options without understanding what is being serialized or why JSON key order differs from list order.
- **Proposed fix:** Keep S06's outcome as deterministic Python structures/order and defer JSON serialization to S08; alternatively, explicitly revise the roadmap and provide a minimal JSON model before code.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F19 🚩 — The helper name and explanation imply a general canonicalizer that the code does not implement.

- **Impact:** The learner may understand rows[-3:] but fail to predict the output because '[r[...] for ...]' and 'any(... for ...)' become additional unknown mechanisms.

### S06-F07 — The absolute wording implies universal total object independence.
- **Category:** TECHNICAL_OVERCLAIM
- **Location:** T1-B paragraph 3
- **Evidence:** The text says 'deepcopy separa todo el grafo'. Python deepcopy recursively copies compound data but deliberately memoizes shared references and returns some immutable/special objects unchanged; it can also copy more than desired.
- **Impact:** A learner can infer that deepcopy guarantees every reachable object is a distinct new object and that all sharing relationships disappear.
- **Proposed fix:** Scope the claim to the course data model: deepcopy recursively copies nested mutable containers so edits to those copied containers do not reach the original; it is broader and more expensive than a shallow copy and is not a universal isolation guarantee.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F08 — The learner is likely to generalize tuple immutability deeply.
- **Category:** MISCONCEPTION_RISK
- **Location:** T1-A paragraph 1 tuple model
- **Evidence:** A tuple is described as a fixed route/container that helpers read without modifying, but no boundary states that tuple immutability prevents replacing its slots, not mutation of a mutable object stored inside a slot.
- **Impact:** A learner can expect t=([1], 'x') to prevent t[0].append(2), but the inner list changes normally.
- **Proposed fix:** Add one sentence: the tuple's positions are fixed, but a mutable object stored inside can still change.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F09 — Bracket lookup means 'raise KeyError if absent'; whether absence is a bug depends on the surrounding contract, not the brackets themselves.
- **Category:** DEFINITION_DRIFT_INVARIANT
- **Location:** T2-A paragraph 2
- **Evidence:** 'd[k] expresa un invariante: la clave debe existir, y KeyError denuncia que el programa rompió esa promesa' reuses the still-broken invariant concept from S03 and makes syntax itself appear to express a domain guarantee.
- **Impact:** A learner can classify every missing bracket lookup as a violated program invariant rather than ask whether missing was expected input and whether get/explicit validation was appropriate.
- **Proposed fix:** Say: use d[k] when the surrounding contract guarantees that key; use get or an explicit check when absence is a legitimate case.
- **Sources (1):** audit/lessons-only/sections/S06.json

### S06-F16 — The learner lacks a stable contrast: set has no sequence order contract; dict preserves insertion order, yet canonical business order may still require sorting.
