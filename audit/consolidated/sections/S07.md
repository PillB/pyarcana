## P1 (11)

### S07-F02 — Every new text/Unicode concept is hidden behind a function-definition/call wrapper unrelated to the concept being taught.
- **Category:** FORGOTTEN_PREREQUISITE
- **Location:** all eight theory code blocks
- **Evidence:** The theory repeatedly wraps examples in def s07_th_N(): ...; the effective S05 ledger left function definition and argument/binding mechanics PARTIAL rather than USABLE.
- **Impact:** A learner may understand NFC or split but still fail to predict whether and when the indented code executes because the wrapper itself is not mastered.
- **Proposed fix:** Use top-level statements for early S07 theory examples; introduce helper functions only where a reusable normalization function is itself pedagogically useful and trace its call explicitly.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F04 — A textual abbreviation is stated as an identity fact rather than a possible representation.
- **Category:** IDENTITY_OVERCLAIM
- **Location:** opening paragraph 3
- **Evidence:** The lesson says 'Ma. del Carmen es la misma persona que María del Carmen' before later insisting that text similarity is only evidence and never proof of identity.
- **Impact:** The learner can conclude that recognizable abbreviation expansion is sufficient to assert two records belong to one person.
- **Proposed fix:** Replace with 'Ma. del Carmen puede ser una abreviatura de María del Carmen; el texto por sí solo no demuestra que dos registros pertenezcan a la misma persona.'
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F05 — The canonical parser fails exactly on compound-surname particles the lesson says it handles and does not route those ambiguous cases to review.
- **Category:** EXAMPLE_CONTRADICTS_PROSE
- **Location:** S07-T1-B name parsing
- **Evidence:** The prose correctly says particles such as de/del/de la can belong to names or surnames, then teaches 'últimos dos tokens = apellidos si hay tres o más'. For 'María Pérez de la Cruz' that heuristic produces given='María Pérez de', apellido1='la', apellido2='Cruz'.
- **Impact:** The learner can split 'de la Cruz' or another compound surname into semantically wrong fields while believing the Latin-American model was handled safely.
- **Proposed fix:** Do not infer surname boundaries from token count alone. Teach a bounded synthetic schema where fields are known, or keep the full normalized name and mark automated component parsing as review when particles make the boundary ambiguous.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F06 — The normalizer alters the local-part without a domain/provider-specific policy authorizing that semantic change.
- **Category:** TECHNICAL_CONTRADICTION_EMAIL_CASE
- **Location:** S07-T2-B normalize_email
- **Evidence:** normalize_email calls raw.strip().casefold() on the entire address. SMTP specifies that the mailbox local-part must be treated as case-sensitive while the domain is case-insensitive; casefold can also expand characters such as ß -> ss.
- **Impact:** Distinct local-parts can be collapsed into one normalized identifier, violating the lesson's own rule to preserve meaning while normalizing representation.
- **Proposed fix:** Preserve local-part case by default; normalize/casefold the domain separately. If a specific provider policy permits local-part folding, make that policy explicit and retain raw.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F07 — The behavior promised by prose (review) is not the behavior shown by the code (uncaught exception).
- **Category:** PROSE_CODE_CONTRADICTION_AND_FUTURE_KNOWLEDGE_LEAK
- **Location:** S07-T2-B email prose + code
- **Evidence:** The prose says a nonconforming email goes to review; normalize_email raises ValueError, and the theory provides no caller that catches that exception and routes it to review. Exception flow is not yet usable and is canonically taught later.
- **Impact:** A learner can believe raising ValueError automatically means the case was safely queued for human review, when execution instead aborts unless another layer catches it.
- **Proposed fix:** Either return an explicit review result using already-taught structures, or teach one bounded exception-signaling sentence and defer catching/routing until the later exception section; do not claim review unless shown.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F08 — The code silently broadens 'dígitos de teléfono/DNI peruano' beyond the ASCII 0-9 symbols the domain example appears to intend.
- **Category:** UNICODE_DIGIT_SEMANTICS
- **Location:** S07-T2-B phone + S07-T3-A DNI regex
- **Evidence:** normalize_phone_pe keeps characters where str.isdigit() is true, and the DNI regex uses \d{8}. Python Unicode semantics include non-ASCII digits; str.isdigit also includes some compatibility digits. Executions retained Arabic-Indic/fullwidth/superscript digits and re.fullmatch(r'\d{8}', '١٢٣٤٥٦٧٨') returned True.
- **Impact:** A learner can accept a synthetic DNI or phone string containing unexpected Unicode digits while believing the code enforces 0-9.
- **Proposed fix:** If the course contract requires ASCII digits, use [0-9]{8} for the synthetic DNI and filter with ch in '0123456789' for the phone; alternatively explicitly state that Unicode decimal digits are accepted and normalize them deliberately.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F09 — A search API is named without its return contract, despite its return value interacting dangerously with previously learned truthiness.
- **Category:** OUTCOME_NOT_TAUGHT / TRUTHINESS_TRAP
- **Location:** S07-T2-A search methods
- **Evidence:** The heading promises split/join/search/replace and the prose lists find/startswith, but theory never explains that str.find returns an index or -1. Because -1 is truthy and 0 is falsy, using if s.find(x): produces wrong decisions at both the first-position and missing cases.
- **Impact:** The learner may write if texto.find('Lima'): and treat a match at index 0 as false while treating 'not found' (-1) as true.
- **Proposed fix:** Teach 'needle in text' for yes/no membership; if find is taught, state explicitly: returns 0..n-1 when found and -1 when absent, so compare against -1 rather than using it as a boolean.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F12 — No-evidence cases receive ordinary numeric similarity scores, including the maximum possible score for empty-vs-empty.
- **Category:** FAIL_CLOSED_CONTRADICTION
- **Location:** S07-T4-A token_jaccard empty handling
- **Evidence:** token_jaccard returns 1.0 when both token sets are empty and 0.0 when only one is empty, while the opening/T4-B policy says missing evidence must go to review rather than receive an invented conclusion.
- **Impact:** Two blank names can appear maximally similar, or one blank name can look like a confident no-match, instead of being recognized as insufficient evidence.
- **Proposed fix:** Return no score (for example None plus reason='sin tokens') when either side has no usable tokens, and route that condition to review separately from similarity.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F14 — The next example silently substitutes an unexplained score from another method or an invented number.
- **Category:** EXAMPLE_CONTRADICTS_PRIOR_FORMULA
- **Location:** S07-T4-B fp_fn_table.py
- **Evidence:** The table assigns score 0.9 to 'José Pérez' vs 'Jose Perez' immediately after defining token Jaccard as the section's similarity score. Under the canonical tokens() implementation those sets have no intersection and Jaccard is 0.0 because NFC/casefold do not remove accents.
- **Impact:** The learner cannot reproduce the displayed evidence and may infer that Jaccard somehow treats accented/unaccented tokens as nearly equal.
- **Proposed fix:** Compute every score using token_jaccard in the example, or label a different metric explicitly and teach it before using it. For José/Jose under current Jaccard, show 0.0 and explain why accent removal is not part of the pipeline.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F15 — The learner is asked to label FP/FN without the external truth value that makes those labels meaningful.
- **Category:** OUTCOME_MODEL_INCOMPLETE
- **Location:** S07-T4-B FP/FN paragraphs
- **Evidence:** FP/FN are defined as cases where the system 'should' or 'should not' match, but theory never introduces the reference label/ground truth needed to know that. The example contains score and decision only, not expected_match.
- **Impact:** The learner can call a high-score pair a false positive based on intuition rather than comparing a prediction against an independently established synthetic truth label.
- **Proposed fix:** Introduce a synthetic expected_match label supplied independently of the text score; define FP/FN as prediction versus that reference. Keep real sensitive identity decisions outside the synthetic exercise.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F16 — The central auditability artifact is described but not demonstrated before practice.
- **Category:** ESSENTIAL_TEACHING_OUTSIDE_LESSON
- **Location:** opening raw/normalized/transforms contract + closing
- **Evidence:** The opening says every exercise uses raw/normalized/transforms and the closing claims each transformation leaves an auditable trace, but none of the theory code blocks actually constructs a record that preserves raw, normalized and an ordered transforms list together.
- **Impact:** The learner can normalize text correctly yet overwrite raw or fail to record which transformation changed the value, while believing the theory already taught the audit contract.
- **Proposed fix:** Add one small theory example that starts from raw, applies NFC/space collapse/case policy step by step, appends named transforms, and returns/prints all three fields without overwriting raw.

### S07-F10 — A new Python string-literal form is introduced at the same time as regex metacharacters.
- **Category:** MICRO_DEFINITION_MISSING

### S07-F11 — Two boundary mechanisms are introduced simultaneously without isolating their responsibilities.
- **Category:** EXPLANATORY_OVERLAP
- **Location:** S07-T3-A anchors/fullmatch
- **Evidence:** The outcome promises anchors ^$, but the prose mainly teaches fullmatch and the code combines ^...$ with fullmatch, so the learner cannot tell which mechanism enforces whole-string coverage. The symbols are never explicitly mapped to start/end.
- **Impact:** The learner can believe fullmatch requires ^/$ or use anchors mechanically without understanding them.
- **Proposed fix:** First teach fullmatch with r'[0-9]{8}'. Then separately define ^ as start and $ as end using search/match examples, noting that anchors are redundant in the preceding fullmatch example.
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F13 — The learner receives the formula without the most important representational information loss caused by converting tokens to a set.
- **Category:** MISCONCEPTION_BOUNDARY_MISSING
- **Location:** S07-T4-A Jaccard model
- **Evidence:** Jaccard is defined over sets but the lesson does not explicitly state that sets discard order and repeated tokens. The implemented score gives 1.0 for 'Juan Perez' vs 'Perez Juan' and for 'Ana Ana' vs 'Ana'.
- **Impact:** A score of 1.0 can be interpreted as textual equivalence even when word order or repetition differs.
- **Proposed fix:** Add one sentence and one counterexample: 'Jaccard de conjuntos ignora orden y repeticiones; 1.0 significa mismos tokens únicos, no mismo texto ni misma persona.'
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F17 — The everyday word 'carácter' is doing two jobs: visible grapheme and Unicode code point.
- **Category:** MICRO_DEFINITION_PRECISION
- **Location:** jobRelevance + T1-A code-point explanation
- **Evidence:** The lesson glosses code points as numbers Unicode assigns to each 'carácter' while its own é example demonstrates that one user-perceived character can be represented by multiple code points.
- **Impact:** The learner can conclude one visible character always equals one code point, then fail to understand combining marks, emoji sequences or length differences.
- **Proposed fix:** Say: 'Un code point es un número asignado por Unicode a una unidad abstracta; un símbolo visible puede estar formado por uno o varios code points.'
- **Sources (1):** audit/lessons-only/sections/S07.json

### S07-F18 — The word 'completa' turns a deliberately narrow business subset into an apparent general email-validity rule.
- **Category:** OVERVALIDATION_WORDING
- **Location:** S07-T2-B email validation prose
- **Evidence:** The prose calls exactly-one-@, nonempty local/domain and no spaces a 'comprobación modesta pero completa', while SMTP syntax permits quoted local-parts and the course itself warns against claiming full email validity.
- **Impact:** The learner may later reject standards-valid addresses as malformed instead of recognizing that the course intentionally supports a restricted subset and routes others to review.
- **Proposed fix:** Rename it 'regla mínima del laboratorio' and state that it defines the subset accepted automatically; other forms may be valid but should be reviewed rather than declared invalid.
- **Sources (1):** audit/lessons-only/sections/S07.json
