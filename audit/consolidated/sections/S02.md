## P1 (8)

### S02-F01 — A syntax scaffold belonging to S05 is used as the container for S02's first worked examples, so the learner must parse a function before focusing on the value/type concept the example claims to teach.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** all non-optional theory code blocks and optional contract code
- **Evidence:** Every main theory example is wrapped in def s02_th_*() or defines safe_int(...); several also carry annotations such as campo: str and valor: str. The V3 roadmap schedules function definition/call/return/parameters and gradual type hints in S05.
- **Impact:** The learner copies def/indentation/call syntax as ritual, cannot explain why the body is indented or why s02_th_1() runs, and may infer that small Python examples require a function wrapper.
- **Proposed fix:** Make S02 theory examples top-level statements. Refactor into functions only when S05 teaches functions; do not add a mini S05 to S02.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F02 — Calling control flow 'support syntax' does not make it cognitively inert: the learner must understand branch selection and iteration to predict the examples.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** opening paragraph 6; T1-B; T2-A code; T2-B truthiness figure; parser code
- **Evidence:** The lesson announces that if and for will appear as support syntax. safe_int depends on if; T2-A uses if/else; the figure explains truthiness; for iterates test values. V3 assigns truthiness/if/elif/else to S03 and for to S04.
- **Impact:** The learner can recite what int() does but cannot explain why safe_int returns one tuple instead of another or why the for block executes multiple conversions.
- **Proposed fix:** Remove if/else/for/truthiness from core S02 theory examples. Demonstrate conversions with separate concrete inputs and show errors directly; defer branching/iteration to S03/S04.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F03 — The lesson requires exception handling to make its main parser outcome work but never teaches what an exception is, where control jumps, or why only a specific exception should be caught.
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** T1-B and T4-B safe_int; T3-B InvalidOperation prose
- **Evidence:** try/except, ValueError capture, InvalidOperation capture, 'no tragar excepciones' and except: pass are central to the parser explanation. V3 places exceptions and recovery boundaries in S09.
- **Impact:** The learner treats try/except as magic punctuation and cannot predict whether the return after try runs, whether except runs, or what happens for an unexpected error.
- **Proposed fix:** Either teach a deliberately bounded micro-model of one recoverable ValueError before the first try/except, or defer robust recovery until S09 and keep S02 to successful conversion plus observable failing examples. Do not silently rely on S09 knowledge.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F04 — A minimal mutable-container preview for aliasing is defensible under the S02 roadmap, but the lesson expands that preview into tuple protocols, slicing, unpacking and typed lists required to follow th
- **Category:** FUTURE_KNOWLEDGE_LEAK
- **Location:** T1-B tuple contract; T2-B list/copy/slice; T3-A tuple unpacking; T4-B errors:list[str]
- **Evidence:** The parser contract returns three-element tuples, for iterates a list, T2-B uses list literals/append/copy/a[:], T3-A uses a,b,c = 10,3,2, and T4-B names list[str]. V3 puts lists/tuples/slicing/unpacking in S06, while S02 only permits identity/mutability/copies 'al nivel necesario'.

### S02-F12 — The lesson turns a mutation guarantee into an identity guarantee.
- **Category:** TECHNICAL_INACCURACY
- **Location:** T2-B str immutability paragraph
- **Evidence:** The prose states that .strip() or concatenation returns another string. Immutability guarantees that the original string is not mutated, not that a distinct object identity must be produced; implementations may reuse the original object when the result is unchanged.
- **Impact:** The learner can predict s is s.strip() must always be False and use identity to reason about string transformations, which is not a valid contract.
- **Proposed fix:** Replace 'devuelve otro string' with 'produce un resultado str sin modificar el original; no bases la lógica en si Python reutiliza o no el mismo objeto'.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F14 — A rule presented as Python-wide changes for the numeric type immediately introduced in T3-B.
- **Category:** TECHNICAL_CONTRADICTION
- **Location:** T3-A operator definitions vs T3-B Decimal
- **Evidence:** T3-A states / returns float and // rounds toward -infinity without restricting operand types. In the same section Decimal division returns Decimal, and Decimal // truncates toward zero (e.g. Decimal(-7)//Decimal(4) == Decimal(-1), while -7//4 == -2).
- **Impact:** The learner applies the int rule to Decimal and predicts the wrong type or wrong negative quotient.
- **Proposed fix:** Scope the rule explicitly: 'con int, / produce float y // hace floor; otros tipos pueden definir estos operadores de otra manera'. In T3-B state Decimal's difference only if // or % will actually be used.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F15 — Approximation error is mislabeled as non-reproducibility, changing the meaning of a core S01 term, and the figure's universal rounding rule conflicts with the paragraph's boundary-based rule.
- **Category:** DEFINITION_DRIFT_TECHNICAL_FALSEHOOD
- **Location:** figure S02-decimal-rounding + T3-B prose
- **Evidence:** The caption says 'con float ni siquiera es reproducible' and 'Redondear una sola vez, al final', while the prose later says quantize at each monetary step that must be shown or persisted. Python documents float's issue as binary representation/round-off, and even provides exact hexadecimal representations useful for reliable portability.
- **Impact:** The learner can believe repeated float operations are random/non-repeatable and cannot tell whether to round once globally or at each defined business boundary.
- **Proposed fix:** Caption: 'Float representa muchos decimales como aproximaciones binarias. Define una política de redondeo y aplícala en los límites de negocio que correspondan; no redondees repetidamente sin una regla'.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F16 — The worked example does not demonstrate the behavior the paragraph explicitly promises.
- **Category:** EXAMPLE_CONTRADICTS_PROSE
- **Location:** T3-B paragraph 3 vs decimal_igv.py

## P2 (13)

### S02-F05 — Individual operations are often described, but the repeated x.algo(...) shape itself remains unexplained.
- **Category:** ORPHAN_SYNTAX
- **Location:** T1-A through T3-B method/attribute syntax
- **Evidence:** The learner meets type(x).__name__, valor.strip(), a.copy(), b.append(), Decimal(...).quantize() and repr-like attributes without a first-use explanation of the dot form.
- **Impact:** The learner cannot distinguish a function call such as int(x) from an operation attached to a value such as x.strip(), so future syntax becomes pattern copying rather than a predictable model.
- **Proposed fix:** Before first dot call add a microdefinition: 'x.metodo() pide al valor x ejecutar una operación propia; no necesitas estudiar objetos todavía'. Avoid __name__ if the attribute itself adds no learning value.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F13 — 'Independizar' sounds total while 'superficial' is an unexplained qualifier.
- **Category:** MISCONCEPTION_RISK
- **Location:** T2-B shallow-copy paragraph
- **Evidence:** The prose says 'Para independizar: a.copy() o a[:] (copia superficial)' without explaining what superficial limits. Python's copy documentation states that a shallow copy creates a new outer compound object but inserts references to the same contained objects.
- **Impact:** The learner can later mutate a nested list through one shallow copy and conclude copy() is broken because the nested element also changed in the other.
- **Proposed fix:** Add one boundary sentence: 'La lista exterior es nueva; si contiene objetos mutables dentro, esos objetos todavía pueden compartirse. Verás copias anidadas en S06'.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F17 — A language-library default is too easily read as a universal business/legal policy.
- **Category:** ROUNDING_POLICY_OVERGENERALIZATION
- **Location:** T3-B paragraph 3
- **Evidence:** ROUND_HALF_EVEN is described as the usual/default 'banking' rounding in a business context without distinguishing Python's default Decimal context from an organization's accounting/tax rule. Decimal exposes multiple rounding modes and quantize can take an explicit one.
- **Impact:** The learner may hard-code HALF_EVEN for a workflow whose documented accounting, tax or contractual rule requires another mode/boundary.
- **Proposed fix:** Say 'Python Decimal's default context uses ROUND_HALF_EVEN, but the business rule must specify the required mode; here we choose HALF_EVEN only as the course convention'.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F18 — A useful input() rule is generalized into a system-boundary rule that will be false in later API/JSON/data lessons.
- **Category:** TECHNICAL_OVERGENERALIZATION
- **Location:** T4-A opening paragraph
- **Evidence:** The paragraph says that in a terminal, web notebook or mobile application the boundary is essentially 'outside = text; inside = meaningful values'. input() does return str, but other application/API boundaries can deliver already-typed booleans/numbers/objects.
- **Impact:** The learner can later assume every external numeric/boolean value must first exist as str and misread typed JSON/API values.
- **Proposed fix:** Limit the claim: 'Con input() y muchos campos de formulario, la entrada llega como texto; otras interfaces pueden entregar tipos distintos'.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F20 — The justification explains away syntax that actually does require a new rule.
- **Category:** FUTURE_KNOWLEDGE_LEAK_MISEXPLANATION
- **Location:** optional contract paragraph about *args and T4-A print signature
- **Evidence:** The lesson says calling print(*valores, sep=...) is merely using a function that accepts several arguments. The leading * is itself iterable argument unpacking, a distinct syntax V3 places with unpacking in S06. T4-A also presents print(*args, sep=..., end=...) before function parameter/keyword-argument models.
- **Impact:** The learner may believe * has no meaning at call sites or confuse print(a,b) with print(*valores).
- **Proposed fix:** Teach print with concrete arguments only: print('a','b',sep=' \| '). Do not show *valores/*args in S02; defer call-site unpacking to S06 and function-parameter semantics to S05.
- **Sources (1):** audit/lessons-only/sections/S02.json

### S02-F21 — 'Basura' suggests random/corrupt data instead of a deterministic approximation and reinforces F15's incorrect reproducibility framing.
- **Category:** LANGUAGE_PRECISION
- **Location:** T3-B danger callout
- **Evidence:** The callout says Decimal(0.1) 'hereda la basura del float'. Python documents that Decimal(float) converts the binary float value exactly to its decimal equivalent; the issue is that the float already represents an approximation of the intended decimal 0.1.
- **Impact:** The learner cannot distinguish deterministic representation error from corrupted or unstable data.
- **Proposed fix:** Replace 'basura' with 'la aproximación binaria ya contenida en ese float'.
- **Sources (1):** audit/lessons-only/sections/S02.json
