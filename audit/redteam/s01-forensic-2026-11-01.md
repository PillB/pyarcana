# PyArcana — forensic audit, S01 and shared mechanics

**Date:** 2026-11-01. **Release decision: NO-GO.** Source baseline `b522f633df8153cc240dd0fa778aa40d2d99ac17`; public deployment observed at [GitHub Pages](https://pillb.github.io/pyarcana/#setup). The fixes described below are local source changes, **not** deployed changes. Structured counterexamples, causal roots, remedies, and disposition live in [the issue ledger](s01-ledger-2026-11-01.json).

## Evidence and boundaries

- **Source census:** 52 section IDs; 416 I Do demonstrations; 1,248 We Do exercises; S01 contributes 8 demonstrations, 24 exercises, and 8 four-choice quiz questions. S01 runtime text, the exported interaction catalog, UI components, progress store, CI specs and tests were inspected. The catalog originally omitted three S01 quiz questions; it was regenerated and given a drift check.
- **Observed desktop live UI:** 1,363 × 936 screenshot plus interactive traversal of all 24 exercise solution controls. A deliberately incorrect response to each of eight quiz questions displayed 0%; Retry plus the authored correct responses displayed 100%. The score ring animated to the score. The completion control was tried repeatedly and exposed a reversible-progress defect.
- **Implementation verification:** red/green test of nested glossary rendering and idempotent progress, unit-level negative controls for data catalog, code complexity, safe environment recipes, and first-use teaching; lint, TypeScript, pedagogy and broad Node adversarial suites. Existing tests and new test output are not proof that production is repaired.
- **Missing evidence:** no successful local Playwright Chromium install (download returned a truncated archive); no CI run on the modified SHA; no runtime event/back-end logs; no full keyboard, zoom, screen-reader or mobile matrix; no six complete distinct runs for every exercise; no deep S02–S52 audit. The live server is the original deployment, not this branch.
- **Global glossary debt surfaced by UX gates:** `scripts/glossary_coverage_audit.py` intentionally allows exactly eight historical missing-introduction hits (`MISSING_PROSE_OWED=8`), with `ok:false` in its report yet a zero exit when the debt count is unchanged. This is an explicit non-regression ratchet, not an accidental missing `sys.exit`; the eight still require curriculum repairs (ledger `S01-RT-020`). Other UX gates passed, but `test:ux-gates` therefore does **not** mean zero glossary debt.

## Screenshot reading order: Z-pattern, desktop

Read coordinates approximately (pixels from screenshot's top-left); the layout changes with scroll. These are **observations**, not a promise that another viewport will match.

1. **First horizontal stroke, x=0–1,363, y=0–58:** the top command bar establishes an `Inicio` entry, section context, navigation to `Proyectos`, `Familiarity`, `Glosario`, `Repositorio`, and appearance/language controls to the right. Multiple destinations compete with the active lesson title; icons need accessible names, meaningful focus order, and visible focus at the sticky top edge. These were not fully keyboard audited.
2. **Down-left diagonal, x=0–285:** a fixed side rail starts with the course progress `0/52`, current section selection and its five substeps. The full 52-section outline is scrollable independently of main content. Some labels are visually truncated; the full destination must survive as accessible text/tooltip. Nested scroll regions can cause wheel/trackpad surprises and focus loss when the lesson is long.
3. **Second horizontal stroke, x≈334–1,190, y≈60–150:** sticky S01 identity, short tagline and a section progress indicator occupy the upper main pane, with the five lesson stages (Teoría → I Do → We Do → You Do → Autoevaluación) available as tabs/rail entries. They convey hierarchy, but need active-tab state, not a color-only cue. Underlying content scrolls under this shell; focus visibility at the sticky boundary remains unverified.
4. **Down the reading column:** title → explanatory body → monospace fenced code or transcript → callout and hint/result → next subsection. On We Do the repeating card hierarchy is `exercise ID + title/kind` → contextual preamble → numbered instruction → starter code → optional hints → `Ver solución` → (when opened) solution and expected output/feedback. The code panel can occupy most of the first viewport and delays seeing feedback; the reveal control is a trust boundary because it exposes an answer, **not** execution of submitted code.
5. **Ending stroke, bottom corners and footer:** floating previous/next arrows are anchored near the lower corners while a small footer is centered. On the observed desktop no catastrophic blocking collision was established; long expanded cards, browser zoom, reduced width and the on-screen keyboard could cause obscuration. These cases are pending and should not be recorded as passing.

**Visual hierarchy finding:** top bar and fixed rail are stable anchors; the main content is readable in a single column, but multiple navigation mechanisms, independent scroll areas and truncated labels impose scanning cost. The open solution adds height with Framer Motion. Rapid repeated click during entry was less reliable than clicking after opacity reached 1; the same target may shift while the panel expands. Root cause cannot be isolated without a frame-by-frame trace, hence issue `S01-RT-016` is unresolved rather than marked fixed.

**Reveal click state machine applied to every card:** `closed` (feedback absent, accessible button name `Ver solución`) → click → `animating open` (content mounted and opacity/height transition) → `open` (feedback visible, button `Ocultar solución`) → click → `animating close` → `closed` (feedback unmounted). The revised E2E asserts absent→visible→absent and opacity=1 before closing. An opening fade becoming fully opaque need not imply height has stopped changing; that is a deliberate outstanding timing uncertainty, not a suppressed failure.

### Eight quiz questions, option states and scoring

Indices are **zero-based source option indices**, not letter labels visible to the learner. In every case the four radio-like choices must be individually selectable, exactly one marked via `aria-pressed`, and correction must be based on the authored answer rather than any choice being accepted.

| Q | Question topic | Correct index | Negative oracle |
|---|---|---|---|
| 1 | Purpose of Python `venv` | 0 | A nonisolating explanation must be wrong. |
| 2 | What belongs in `.gitignore` | 2 | Versioning the virtualenv/secret must be wrong. |
| 3 | Conventional Commits message | 3 | Unstructured misleading message must be wrong. |
| 4 | Reproduce another developer's environment | 1 | An install without declared dependencies must be wrong. |
| 5 | Why `.env` must not go to GitHub | 0 | Exposing real secrets must be wrong. |
| 6 | Meaning of Python exit code 1 | 2 | Calling it successful completion must be wrong. |
| 7 | Ruff project configuration file | 3 | Claiming it resides in arbitrary code file must be wrong. |
| 8 | Why not force-push shared `main` | 1 | Treating history rewrite as harmless must be wrong. |

**Live observable transitions:** before submit, selection visually updates; after eight deliberately wrong authored indices, result reads `0%`; retry reopens unanswered selection; eight source-correct choices then yield `100%` with positive feedback and animated ring. The quiz answer cardinality is **4⁸ = 65,536** complete response vectors, before retry permutations and timing; testing one all-wrong and one all-right vector is **not** an exhaustive matrix. The strict CI spec now covers both extreme outcomes, retry, persistence and repeated completion but has not run against the changed SHA. A useful next property-based test would generate bounded answer vectors and assert `score = 100 × correct_count/8` (subject to actual product rounding), selection isolation and no post-submit mutation.

## Root causes and tiered remediation strategy

1. **P0 / data loss and learner progress:** distinguish irreversible shell/Git actions; require preconditions, explicit intent and recoverability. Make completion operations monotonic/idempotent, not toggles disguised as marking. Keep store and server merge/integration semantics under adversarial concurrent/reload tests.
2. **P1 / measurement integrity:** tests must be falsifiable; derive the catalog from authoritative source and fail stale artifacts, include negative controls, verify feedback and persistent result. No `catch {}` to hide a missing required click. Treat illustrated `tests` checklists honestly as self-checks; do not market them as remotely verified execution.
   A broad Python adversarial rerun exposed a further diagnostic-hiding fault in `tools/fixer/apply_patches.py`: unrelated npm warnings on stderr displaced real TypeScript failures printed on stdout. The subprocess helper now preserves both channels and has a direct injected-warning regression test (ledger `S01-RT-021`).
3. **P1 / teaching correctness:** check command recipes by platform, shell and environment; source fact claims from primary literature; guard first-use jargon in actual render order. A glossary tooltip alone does not substitute for an accessible first explanation.
4. **P1 / cross-cutting architecture:** preserve 52 IDs and progress keys while applying shared renderer/quiz fixes. Complexity gate must reject **new** >15 functions regardless of deleted old debt. Existing 32 grandfathered offenders (worst 78) are tracked debt, not standards compliance.
5. **P1–P2 / perception and inclusion:** capture 320 CSS px reflow and 200/400% zoom, keyboard-only focus route, screen-reader announcements, high contrast, reduced motion and every transition boundary. Check sticky/floating overlap, long code overflows, independent scroll panes, sidebar ellipses and accidental double taps.
6. **Release assurance:** run exact changed SHA on GitHub CI, fix failed Playwright/trace observations, recheck deployed content and hashes. Then separately scale the 5+5+4 framework to S02–S52, prioritizing unlike execution mechanics and data/scientific assumptions. Do not substitute structural census for 51 forensic audits.
