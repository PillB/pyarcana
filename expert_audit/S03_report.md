## 2. Executive Summary of Quality

**Overall score: 5.5 / 10**

**Verdict.** Section 3 has **excellent pedagogical architecture** — tight
I-Do / We-Do / You-Do fidelity, a coherent tri-estado (`accept/reject/review`)
narrative, strong guard-clause pedagogy, well-aligned self-check, and the
best integration of capstone increment language (`CP-N1-A`) seen so far.
**However, it is undermined by repeated code/output integrity failures in
the I-Do and We-Do tabs**: print-label / value / output triples that do not
agree, fabricated `output:` strings that contradict what Python would
actually produce, and at least one logically impossible membership verdict.
The section explicitly commands the learner "no inventes resultados" while
itself containing invented results. This is the single most damaging class
of defect in S03 and the reason the score is held at 5.5 rather than the
8.0–8.5 the pedagogy would otherwise earn.

**Headline findings (top 5):**

1. **CRITICAL — I-Do `S03-T1-A-DEMO` fabricated output (Issue C-01).** The
   printed labels (`'Sucursal-Sur'`), the compared values (`"Sucursal-Centro"`),
   and the claimed output (`'Sucursal-Norte' → True`) are **three different
   strings**, and the membership verdict for `region in ALLOWED` is wrong
   (output says `True` for `"Cliente-B" in {"Sucursal-Norte","Arequipa","Cusco"}`,
   which is actually `False`).
2. **CRITICAL — I-Do `S03-T3-A-DEMO` fabricated output (Issue C-02).** Input
   list contains `("Cliente-A", 30), …, ("Cliente-B", 15)` but the claimed
   output prints `Sucursal-Norte … accept` / `Sucursal-Sur … reject`. Both
   the labels and the accept/review verdicts are wrong.
3. **CRITICAL — We-Do `S03-T1-B-E2` four-way inconsistency (Issue C-03).**
   The instruction, the tests contract, the solutionCode print label, the
   solutionCode passed value, and the claimed output use **five different
   synthetic-data strings** (`'Lima'`/`'Sucursal-Norte'`/`'Oficina-Este'`/
   `'Oficina-Oeste'`/`'Cliente-A'`/`'Cliente-B'`) for the same slot.
4. **HIGH — File/title mismatch (R-01).** File is `s03-data-structures.ts`
   and `id: 'data-structures'`, but the section explicitly **disclaims**
   data structures ("No es entrega de esta sección: parsers CSV/JSON…").
   This is residue of a prior curriculum plan.
5. **MEDIUM — Synthetic-data refresh drift (systemic).** Across multiple
   exercises the literal set members, the loop input tuples, and the
   expected output strings drift between `Lima/Arequipa/Cusco/Piura/Tacna`
   and `Cliente-A/B · Sucursal-Norte/Sur/Centro · Oficina-Este/Oeste`.
   It looks like a PII / real-place-name sanitization pass was applied
   inconsistently across `instruction`, `hints[]`, `tests`, `starterCode`,
   `solutionCode.code`, and `solutionCode.output`. (Issues C-01..C-07,
   plus R-04.)

**Strengths to preserve:**
- Clear tri-state contract (`accept/reject/review`) carried through theory →
  I-Do → We-Do → You-Do → self-check.
- Strong "no confundas `None` con `0`" through-line; reinforced in callouts,
  hints, feedback, and the self-check.
- T1→T4 progressive disclosure (booleanos → control → reglas → verificación)
  with a `Ritmo sugerido (~18 h)` block per section opener.
- Each We-Do sub-topic follows **E1 guiado → E2 independiente → E3
  transferencia** — the canonical scaffolded-release pattern.
- `starterCode` always carries a `# DEFECT: …` comment teaching the learner
  *what* to fix, not just *that* it's broken.
- Self-check (8 MCQs) covers every T-sub-topic with calibrated distractors
  and accionable explanations.
- Resources list is high-quality and on-topic (PEP 636, Python docs, CS50P,
  MIT 6.100L, Fluent Python, Python Crash Course).

## 3. Detailed Issue Registry

Severity legend: **C**=Critical (blocks learning or contains falsehood),
**H**=High, **M**=Medium, **L**=Low. Pedagogical impact is qualitative.

### Code/Output integrity (C-01 … C-08)

#### C-01 · I-Do `S03-T1-A-DEMO` — fabricated print labels & wrong verdict
- **Severity:** Critical
- **Location:** `iDo.steps[0]` (lines ~397–416 of source).
- **Evidence (code as written):**
  ```python
  region = "Cliente-B"
  ALLOWED = {"Sucursal-Norte", "Arequipa", "Cusco"}
  print("region == 'Sucursal-Sur' →", region == "Sucursal-Centro")
  print("region != 'Oficina-Este' →", region != "Oficina-Oeste")
  print("region in ALLOWED →", region in ALLOWED)
  print("'Cliente-A' not in ALLOWED →", "Cliente-B" not in ALLOWED)
  ```
- **Evidence (claimed output):**
  ```
  region == 'Sucursal-Norte' → True
  region != 'Sucursal-Sur' → True
  monto >= 1000 → True
  monto < 500 → False
  region in ALLOWED → True
  'Sucursal-Centro' not in ALLOWED → True
  1000 <= monto <= 2000 → True
  ```
- **What Python would actually print:**
  ```
  region == 'Sucursal-Sur' → False
  region != 'Oficina-Este' → True
  monto >= 1000 → True
  monto < 500 → False
  region in ALLOWED → False
  'Cliente-A' not in ALLOWED → True
  1000 <= monto <= 2000 → True
  ```
- **Pedagogical impact.** This is the **first I-Do demo of the section** — the
  learner's first encounter with the comparison/membership vocabulary. The
  print label, the comparison value, and the output line all show **different**
  strings for the same slot, and the membership verdict is wrong. A learner
  who runs this in Pyodide will see `region in ALLOWED → False` and conclude
  either (a) the course is wrong, (b) they broke something, or (c)
  `in` works differently than they thought. The I-Do intro literally says
  "no inventes resultados" two paragraphs above. **Trust erosion at minute 0.**

#### C-02 · I-Do `S03-T3-A-DEMO` — fabricated labels & wrong accept verdict
- **Severity:** Critical
- **Location:** `iDo.steps[4]` (lines ~510–537).
- **Evidence (code):**
  ```python
  ALLOWED_REG = {"Oficina-Este", "Arequipa", "Cusco", "Oficina-Oeste"}
  for r, e in [("Cliente-A", 30), ("Tacna", 30), ("Cliente-B", 15), (None, 40)]:
      print(r, e, "→", rule_region_edad(r, e))
  ```
- **Claimed output:**
  ```
  Sucursal-Norte 30 → accept
  Tacna 30 → review
  Sucursal-Sur 15 → reject
  None 40 → review
  ```
- **Actual output:**
  ```
  Cliente-A 30 → review     # "Cliente-A" not in ALLOWED_REG → review, NOT accept
  Tacna 30 → review
  Cliente-B 15 → reject
  None 40 → review
  ```
- **Pedagogical impact.** The learner is being shown a *successful* accept for
  a region that is **not** in the allowlist — the exact opposite of what the
  section teaches. Combined with label swaps (`Cliente-A`→`Sucursal-Norte`),
  the demo invalidates the rule it is supposed to demonstrate.

#### C-03 · We-Do `S03-T1-B-E2` — five-string slot drift
- **Severity:** Critical
- **Location:** `weDo.steps[5]` (lines ~838–878).
- **Evidence (instruction):** lists `'Lima' or 'default'` with contract
  `default, Lima, 0, 99, 0`.
- **Evidence (`tests`):** `'assert results: default, Sucursal-Norte, 0, 99, 0'`
  — introduces `Sucursal-Norte` for the same slot.
- **Evidence (`solutionCode.code`):**
  ```python
  print("'Oficina-Este' or 'default' →", "Oficina-Oeste" or "default")
  ```
  The label says `Oficina-Este` but the value passed is `Oficina-Oeste`.
- **Evidence (`solutionCode.output`):**
  ```
  'Cliente-A' or 'default' → Cliente-B
  ```
  Fourth different string pair for the same slot.
- **Actual Python output of `solutionCode.code`:**
  ```
  '' or 'default' → default
  'Oficina-Este' or 'default' → Oficina-Oeste
  0 and 99 → 0
  5 and 99 → 99
  None or 0 → 0
  ```
- **Pedagogical impact.** Five different synthetic strings (`Lima`,
  `Sucursal-Norte`, `Oficina-Este`, `Oficina-Oeste`, `Cliente-A`/`B`) appear
  for the same data slot across four fields of one exercise. The learner
  cannot tell what they are supposed to predict. Worse, the **claimed output
  is a fabrication** — Python will never print `'Cliente-A' or 'default' →
  Cliente-B` from this code.

#### C-04 · We-Do `S03-T1-A-E1` — instruction / hint / solution disagree on region labels
- **Severity:** High
- **Location:** `weDo.steps[0]` (lines ~670–717).
- **Evidence.**
  - `instruction` says `region = "Cusco"`, expects booleanos for `region ==
    "Lima"` (False) and `region != "Piura"` (True).
  - `hint` says: `region == "Sucursal-Centro" es False` — a *third* label.
  - `solutionCode.code` actually runs `region == "Cliente-A"` (False) and
    `region != "Cliente-B"` (True) — a *fourth* pair.
  - `starterCode.code` uses `region != "Oficina-Este"` and
    `region == "Oficina-Oeste"` — a *fifth* pair.
- The expected boolean tuple (True, True, True, False, True) is preserved
  across all five variants, so the *contract* is consistent — but the labels
  are not, and the learner will be confused which print to write.

#### C-05 · We-Do `S03-T3-A-E1` — three-way data drift, fabricated output
- **Severity:** Critical
- **Location:** `weDo.steps[12]` (lines ~1286–1334).
- **Evidence.**
  - `instruction`: `ALLOWED = {"Lima","Arequipa","Cusco","Piura"}`; tests
    `Lima, Tacna, None`; expected `accept, review, review`.
  - `tests`: `'assert Sucursal-Norte accept, Tacna review, None review'`
    (label drift).
  - `starterCode`: `ALLOWED = {"Sucursal-Sur","Arequipa","Sucursal-Centro","Oficina-Este"}`; loops `["Oficina-Oeste", "Tacna", None]`.
  - `solutionCode.code`: `ALLOWED = {"Cliente-A","Cliente-B","Sucursal-Norte","Sucursal-Sur"}`; loops `["Sucursal-Centro", "Oficina-Este", None]`.
  - `solutionCode.output` (claimed):
    ```
    Oficina-Oeste → accept
    Cliente-A → review
    None → review
    ```
- **Actual Python output of `solutionCode.code`:**
  ```
  Sucursal-Centro → review    # not in set → review, not in code's loop list at all
  Oficina-Este → review       # not in set → review
  None → review
  ```
- The claimed output references inputs (`Oficina-Oeste`, `Cliente-A`) that
  are **not** in the solution's loop list, and one of them (`Cliente-A`) **is**
  in the allowlist, so a correct run would print `Cliente-A → accept`, not
  `review`. Three layers wrong.

#### C-06 · We-Do `S03-T3-A-E3` — `RUC` listed in instruction but absent in starter
- **Severity:** Medium
- **Location:** `weDo.steps[14]` (lines ~1388–1441).
- **Evidence.** `instruction` says test cases include `RUC`. The
  `starterCode` only iterates `[("DNI","12345678"), ("DNI","123"), (None,"1")]`
  — `RUC` is missing. The `solutionCode` does iterate `[…, ("RUC","20123456789"), …]`.
  The starterCode therefore does **not** exercise the `NOT_IN_ALLOWLIST` path
  the way the instruction promises, which weakens the "DEFECT" the student
  must repair. Cosmetic, but breaks the E3 transfer pattern (the student
  cannot observe the bug in RUC because RUC is not in the starter).

#### C-07 · We-Do `S03-T2-A-E2` — `solutionCode` `bad` still produces accept for 95
- **Severity:** Low (correct, but pedagogically muddy)
- **Location:** `weDo.steps[7]` (lines ~978–1037).
- **Evidence.** The `instruction` says: *"La función `bad` usa ifs
  independientes y clasifica mal el 95 (queda review porque el segundo
  `if score >= 50` pisa el accept)."* The `solutionCode` re-defines `bad`
  with three independent ifs (`if score >= 80: status = "accept"; if score
  >= 50: status = "review"; if score < 50: status = "reject"`). For input
  95: first sets `accept`, second overwrites to `review`. ✅ Output
  `95 bad= review good= accept` is correct. The issue is that the
  `starterCode` `bad` is identical to the `solutionCode` `bad` (so the
  student doesn't have to *fix* `bad`, they only have to *add* `good`).
  Pedagogically the E2 is fine; the starter could have left `good` as a
  stub to make the "fix" task concrete.

#### C-08 · We-Do `S03-T4-A-E3` — solutionCode `validate_edad_fixed` returns `review` for edad 70–120
- **Severity:** Medium (semantic)
- **Location:** `weDo.steps[17]` (lines ~1725–1789).
- **Evidence.** `validate_edad_fixed`:
  ```python
  if e is None: return "review"
  if not isinstance(e, int): return "reject"
  if e < 0 or e > 120: return "reject"
  if e < 18: return "review"
  if e <= 65: return "accept"
  return "review"        # 66 ≤ e ≤ 120 → review
  ```
  The invariante text printed says: *"menores y ausentes → review; solo
  fuera de 0-120 o tipo mal → reject"*. But the code puts 66–120 (e.g.,
  edad 80) in `review`, not `accept`. This contradicts both the invariante
  text and the prior T2-A contract that `18 ≤ edad ≤ 65 → accept` (so 66+
  should be `reject` in a strict policy, or `accept` if the business
  allows adults). The exercise's narrative ("adjust the invariante")
  technically licenses this, but the printed invariante text and the code
  don't fully agree — a student following the invariante would not write
  the `return "review"` for 66–120.

### Meta-leak / identity issues (R-01 … R-04)

#### R-01 · File name and `id` say "data-structures" but section title says "Decisiones y reglas"
- **Severity:** High (meta-leak / curriculum drift)
- **Evidence.** File `src/lib/course/sections/s03-data-structures.ts`,
  `id: 'data-structures'`. The theory opener explicitly disclaims data
  structures: *"Las colecciones avanzadas y archivos (list/dict profundos,
  CSV/JSON) se trabajan más adelante en el currículum de datos."* The
  callout titled "Fuera de alcance en esta sección" reinforces it.
- **Impact.** The filename is residue of a prior curriculum plan in which
  Section 3 covered data structures; the content was swapped to control
  flow / validation rules without renaming the file. URL slug
  (`/section/data-structures`) and GitHub history will carry this drift.
  Not user-facing text per se, but it qualifies as design-note leakage into
  the project structure, and breaks the "the file name is the topic"
  convention that S01 (`s01-setup`) and S02 (`s02-basics`) honor.

#### R-02 · `CASO-LIM-003` referenced as a learner-visible fixture id
- **Severity:** Low (intentional, but worth noting)
- **Evidence.** The string `CASO-LIM-003` appears in user-facing prose
  (theory opener, weDo intro, every weDo `instruction` as `· CASO-LIM-003`),
  and in code comments (`# CASO-LIM-003 · …`). Treated as a known

- **Impact.** Intentional cross-section tracking. Not a leak per se, but if

  orphan meta-text. Document the convention in `README.md` of the repo

#### R-03 · Inline capstone identifiers `CP-N1-A`, `S02` in prose
- **Severity:** Low (intentional roadmap connective tissue)
- **Evidence.** `jobRelevance`, `callout.content`, `youDo.context`,
  `portfolioNote` all reference `CP-N1-A` and `S02`.
- **Impact.** This is the desired "capstone increment" connective tissue
  and is *good*. The only improvement is to ensure `CP-N1-A` is defined in
  a glossary the first time the learner meets it (the section does explain
  it parenthetically as "validate por campo con accept/reject/review"). No
  fix needed unless the glossary is missing course-wide.

#### R-04 · Synthetic-data refresh drift (systemic)
- **Severity:** High (root cause of C-01..C-05)
- **Evidence.** See C-01..C-05. The same data slot cycles through
  `Lima/Arequipa/Cusco/Piura/Tacna` (real Peruvian regions, original
  draft) and `Cliente-A/B · Sucursal-Norte/Sur/Centro · Oficina-Este/Oeste`
  (synthetic replacements) **within the same exercise**. The replacement
  was applied field-by-field (instruction → solution → output) at different
  times or by different search/replace passes, leaving the section in a
  broken state.
- **Impact.** This is the dominant quality defect of S03. Fixing requires a
  full pass per exercise to make `instruction ↔ hints ↔ tests ↔
  starterCode ↔ solutionCode.code ↔ solutionCode.output` reference one
  single, coherent dataset.

### Pedagogical structure & cognitive load (P-01 … P-06)

#### P-01 · We-Do `S03-T1-A-E2` — feedback mentions "RUC" without context
- **Severity:** Low
- **Evidence.** `feedback`: *"Allowlists literales fallan en silencio si no
  normalizas mayúsculas. Documenta el contrato."* — fine. But the test list
  includes `"RUC"` and the feedback doesn't mention the policy
  implication (RUC is a different document type in Peru — Registro Único de
  Contribuyentes — not just "not in set"). For Peruvian Spanish audience,
  a one-line aside ("RUC no es tipo de documento personal, es fiscal")
  would sharpen the example.

#### P-02 · Theory T1-A — `set` membership is introduced before `set` is taught
- **Severity:** Medium
- **Evidence.** T1-A paragraph 2: *"Para allowlists de códigos fijos, un
  **`set` de literales** es ideal: lectura clara y chequeo O(1)."* The set
  literal `{"Lima","Arequipa",...}` appears in the very first theory code
  block. But `set` is not introduced until later (collections, which the
  section explicitly defers). The learner meets `{...}` syntax before
  being told what it is.
- **Impact.** Minor cognitive load bump; learners may think `{}` is a dict.
  Mitigation: add a parenthetical "(un `set` es una colección sin
  duplicados; lo verás a fondo más adelante)" on first use.

#### P-03 · Theory T3-B — `match/case` introduced before its prerequisites
- **Severity:** Medium
- **Evidence.** T3-B introduces `match/case` (Python 3.10+). The callout
  says "El curso asume 3.12+" — fine. But the weDo exercises immediately
  use OR patterns and `case _`. There is no We-Do exercise that introduces
  `match` from scratch with a single case. The E1 of T3-B jumps to building
  a decision table; the learner who hasn't seen `match` may struggle.
- **Impact.** Consider an "E0" micro-demo or an extra callout that shows
  the simplest possible `match` (one case + wildcard) before the OR
  patterns.

#### P-04 · I-Do intro — claim "no inventes resultados" contradicted by demos
- **Severity:** Critical (meta-pedagogical)
- **Evidence.** `iDo.intro`: *"Observa la salida embebida y compárala con
  lo que ves al correr el código; no inventes resultados."* `weDo.intro`:
  *"Ejecuta y compara con la salida del solution; no inventes resultados."*
  Yet C-01, C-02, C-03, C-05 all show fabricated or inconsistent outputs.
- **Impact.** The instruction is correct; the section fails to live up to
  it. This is the single most corrosive pedagogical finding: the rule the
  section preaches is the rule the section violates.

#### P-05 · You-Do `validate_monto` — outlier threshold (50000) introduced silently
- **Severity:** Low
- **Evidence.** `youDo.starterCode` `validate_monto` returns `NEEDS_REVIEW`
  for `valor > 50000`. The number 50000 is not introduced in any T-theory
  paragraph; it appears only in weDo S03-T3-A-E2 (where the same threshold
  is used). Learner has to reverse-engineer the threshold from the test
  assertions.
- **Impact.** Minor; the `_run_tests` asserts document it implicitly.
  Consider surfacing the threshold in `portfolioNote` as a tunable
  constant.

#### P-06 · Self-check Q4 distractor `"default"` is the only Spanish-free option
- **Severity:** Low
- **Evidence.** `selfCheck.questions[3].options`: `['True','False','""','"default"']`.
- **Impact.** The correct answer is the only non-Spanish (pure code) one.
  Students can pattern-match on "the code-looking one" without
  understanding. Consider `['Verdadero','Falso','""','"default"']` so all
  distractors look equally code-adjacent.

#### G-03 · Mixed Spanish/English jargon density in `tagline` and `jobRelevance`
- **Severity:** Medium
- **Evidence.** `tagline`: accept/reject/review, falsy, short-circuit.
  `jobRelevance`: parser, intake, falsy, truthiness, allowlists, decision
  tables, guards.
- **Impact.** This is intentional code-switching for a tech audience and is
  acceptable in Peruvian Spanish data-science registers. However, the
  *first* occurrence of each English term in the `theory` blocks should

  table`, `short-circuit`, `match`, `case`, `wildcard`, `outlier`.
- **Improvement.** Add a one-line "Diccionario de la sección" callout at
  the top of theory T1-A mirroring the S01 "Diccionario del día 1"
  pattern. This is a comparative-quality gap: S01 has the gold-standard
  dictionary block, S03 doesn't.

#### G-04 · Theory T4-B paragraph 1 — long sentence with embedded code, FH ≈ 38
- **Severity:** Medium
